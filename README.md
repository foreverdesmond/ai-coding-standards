## 这是什么

这是一套面向 AI 辅助开发和多 Agent 协作的软件工程规范。

它的目标是把一个尚未完全明确的开发目标，转化为可审核、可实现、可验证、可合并、可追溯的软件变更。

它不绑定特定的编程语言、技术框架、数据库、代码托管方式或 AI 模型。无论是一个人借助 AI 开发，还是多个 Agent 并行协作，都可以根据任务风险选择适当的流程。

产品应该做什么，始终由人类决定；具体的调查、设计、实现和验证，则交给职责明确的 Agent 协作完成。使用 AI 开发软件时，最需要控制的是：

> 在使用 AI 开发软件时，如何控制开发范围、职责边界、执行权限、验证证据和最终质量。

## 为什么需要它

AI 已经能够快速调查代码、生成实现、编写测试和完成大量工程工作。但“代码生成完成”不等于“软件变更可信”。在真实的 AI 辅助和多 Agent 开发中，容易反复出现以下问题：

| 风险           | 典型表现                                                                                |
| -------------- | --------------------------------------------------------------------------------------- |
| 事实漂移       | Agent 依据旧文档、过期上下文或其他 Agent 的总结工作，却没有重新核对当前代码和运行事实。 |
| 伪完成         | 单元测试通过、项目能够编译，就被误认为系统已经正确。                                    |
| 过度信任上下文 | 上下文包被当成事实本身，代码已经变化却仍然按照旧地图实施。                              |
| 自审自批       | 编写代码、审核代码、执行合并由同一个主体完成。                                          |
| 不安全执行     | Agent 为了测试方便，未经授权创建、删除或清空数据库及其他真实资源。                      |
| 状态不可恢复   | 任务中断后无法准确判断进度、证据和下一步动作，过程也无法审计。                          |
| 设计偏离       | 实现已经偏离需求或设计，但被绿色测试结果掩盖。                                          |

单人开发时，这些风险往往依靠开发者的经验、记忆和持续盯防来控制。多 Agent 并行工作后，单靠个人注意力很难维持同样的控制水平，因此必须把这种控制能力固化为角色、文档、证据和门禁。

这份规范来自真实的 AI 辅助开发实践。开发中遇到的问题经过复盘后，被整理为可复用的工程规则。

## 它解决什么问题

本规范将常见风险转换为可执行的控制机制：

| 要解决的问题           | 对应机制                                                                  |
| ---------------------- | ------------------------------------------------------------------------- |
| 不知道当前事实是什么   | 当前代码、配置、运行入口和可复核证据优先；文档和上下文只作为受控导航。    |
| 不知道任务是否真正完成 | 通过 Level 0–3 分层验证，区分局部正确、集成正确、系统正确和真实环境正确。 |
| 没有人独立检查结果     | 分离需求与设计、实现、审核、集成、验证和调度职责。                        |
| Agent 的操作范围不可控 | 明确修改范围、读取范围、外部资源边界和人工授权边界。                      |
| 任务状态容易丢失       | 使用持久、可恢复、可审计的任务台账和证据状态。                            |
| 流程过重或过轻         | 按风险选择轻量、标准或高风险路线。                                        |
| 代码通过但设计错误     | 将需求一致性、设计一致性和 SOLID 原则纳入质量门禁。                       |

## 人类与 Agent 如何分工

人类不需要管理每一行代码，应该把注意力放在真正需要人类负责的判断上。

人类主要负责：

- 明确产品目标、业务优先级和成功标准；
- 确认本次做什么、不做什么；
- 划定数据、权限、安全和外部操作边界；
- 判断风险是否可接受，以及哪些事项需要单独授权；
- 在关键门禁处审核证据并决定是否进入下一阶段；
- 批准合并、发布以及其他具有业务或外部影响的操作。

Agent 主要负责：

- 调查当前代码、配置、运行路径和相关事实；
- 将已确认的目标展开为需求、设计和开发任务；
- 编写、修改和验证代码；
- 执行独立审查、集成和分层验证；
- 记录状态、证据、风险和未完成事项；
- 在规定的权限和职责范围内推进任务。

人类仍然需要理解软件质量，只是不必承担全部实现细节。更重要的判断包括：需求是否正确、范围是否清晰、边界是否关闭、证据是否充分、风险是否可控，以及最终成品是否值得交付。

## 六个核心角色

这六个角色对应传统软件开发流程中的职责分工：

```text
需求与设计 → 实现 → 独立审查 → 集成 → 验证 → 调度协调
```

| 角色                | 主要职责                                                 |
| ------------------- | -------------------------------------------------------- |
| Doc/Design Reviewer | 上下文文档的制作、各类文档的编写与审核。                 |
| Implementer         | 在独立任务分支中完成实现、返工和局部验证。               |
| Reviewer            | 基于准确的代码差异、提交和证据进行独立审查。             |
| Integrator          | 合并已经审核通过的精确提交，处理集成冲突。               |
| Validator           | 执行合并后的集成验证、系统验证和回归验证。               |
| Coordinator         | 负责任务派发、状态管理、证据消费、暂停、恢复和门禁协调。 |

角色可以根据任务风险进行适度裁剪或兼任，但开发者不得批准自己的任务，合并执行者不得替代独立审查，最终业务批准不得由 Agent 自行完成。

当前项目采用 Hermes 作为 Coordinator 的一种实现。规范定义的是调度职责、状态边界和控制要求，其他项目可以采用不同的调度实现。

## 如何使用这套规范

使用这套规范时，先与 AI 共同把问题定义清楚，再由相应角色的 Agent 完成工程展开和实施。

### 1. 与 AI 讨论目标，形成背景与需求

从一个尚未完全明确的想法开始，与 AI 讨论：

- 为什么要做这件事；
- 当前系统、业务或使用场景是什么；
- 用户希望得到什么结果；
- 本次需要解决什么问题；
- 哪些内容明确不在本次范围内；
- 有哪些约束、风险和外部依赖；
- 最终如何判断它已经完成。

AI 可以帮助提问、调查、整理事实、识别矛盾和发现遗漏，并形成：

- 任务背景与现状分析文档；
- 需求规格文档。

这两个文档应在讨论、调查和确认中不断完善，内容随着事实和决定的确认而收敛。

### 2. 关闭需求边界

进入设计和编码之前，应尽可能关闭本次任务的关键边界，包括：

- 功能范围与非功能范围；
- 用户行为、系统行为和异常处理；
- 输入、输出、数据和权限边界；
- 安全边界以及不可自动执行的操作；
- 外部系统和持久化资源的操作范围；
- 不同环境下的行为差异；
- 验收方式和验证等级；
- 已确认的决定、待确认事项和明确不解决的问题。

“关闭边界”并不意味着所有未知信息都必须消失。无法确认的内容应记录为未知、假设、风险或待授权事项，不能由 Agent 在后续阶段自行补全为事实或需求。

当背景和需求文档已经足够明确，范围、验收口径和安全边界得到确认后，才进入工程展开阶段。

### 3. 由相应 Agent 完成工程展开

背景与需求边界确认后，由相应角色的 Agent 继续完成：

- 详细设计；
- 开发任务拆分；
- 任务依赖和交界责任；
- 文件与资源所有权；
- 上下文包和任务委派信息；
- 验证计划与证据要求。

人类不需要逐项编写技术实现细节，但需要确认设计和任务拆分是否仍然符合已经批准的目标与边界，是否引入了未经批准的新需求，以及每个任务是否具备清晰的完成条件。

### 4. 任务拆分完成后进入编码阶段

编码开始前，需求、设计和开发任务必须已经形成可执行的任务链。每项任务都应有明确的范围、责任、依赖、验证方式和完成条件。

之后由各角色按照职责推进：

```text
Implementer 实现
  → Reviewer 独立审查
  → Integrator 集成
  → Validator 分层验证
  → 人类在关键门禁处作出授权决定
```

人类不必持续介入每一行代码的编写，但必须在需求确认、边界关闭、设计批准、风险授权、验证结论以及合并发布等关键节点进行判断。

## 适用范围与迭代边界

本规范不适合用来一次性规划、拆解和驱动整个大型项目。

大型项目通常包含长期演进的业务目标、持续变化的技术约束和大量尚未暴露的不确定性。如果一开始就让 Agent 完成整个项目的需求、设计和任务拆分，容易形成过期上下文、过度设计和难以维护的任务链。

本规范的最佳实践，是应用于传统敏捷开发中一个 Sprint 所对应的、边界清晰且可以独立验收的一组开发任务：

1. 选择一个明确的迭代目标；
2. 与 AI 共同完成背景调查和需求确认；
3. 关闭本次迭代的范围、风险和安全边界；
4. 由 Agent 完成设计和开发任务拆分；
5. 通过独立审核后进入编码；
6. 完成分层验证、集成和合并；
7. 根据本次迭代的真实结果，确定下一次迭代的目标。

大型产品应通过多次增量迭代形成。每次迭代都从明确的 Sprint 目标开始：

```text
产品愿景
  → Sprint 目标
  → 背景与需求确认
  → 设计与任务拆分
  → 编码与独立审查
  → 集成与分层验证
  → 形成可交付增量
  → 复盘并进入下一次 Sprint
```

每次迭代都应以当前真实代码、运行状态和已验证结果作为新的事实基础。上一轮的假设和上下文，只有经过重新核对后才能继续使用。

本规范服务于大型项目的增量交付，应在每次 Sprint 中反复使用。

## 验证：从局部正确到真实可交付

测试结果需要结合验证范围和运行环境解读。本规范将验证分为多个层级：

| 等级    | 要回答的问题                                   |
| ------- | ---------------------------------------------- |
| Level 0 | 这项任务本身是否按照需求和设计正确实现？       |
| Level 1 | 多个任务组合后，迭代内的集成行为是否正确？     |
| Level 2 | 系统按生产形态运行时，关键路径是否正确？       |
| Level 3 | 在真实外部环境中，版本级业务结果是否满足要求？ |

> 单元测试通过，只能证明局部行为满足当前测试；它不能自动证明系统接线、真实环境和最终业务结果正确。

如果某一验证等级不适用，必须记录理由、风险和后续责任人，不能把未验证的内容默认为正确。

## 按风险选择流程强度

本规范不要求所有任务都走同样复杂的流程。项目应根据任务的影响范围、可逆性、外部依赖和失败代价，选择合适的路线：

| 路线   | 适用场景                                                      | 典型要求                                               |
| ------ | ------------------------------------------------------------- | ------------------------------------------------------ |
| 轻量   | 局部、可逆、影响小、自动化充分的变更                          | 任务说明、定向验证、独立第二视角审查。                 |
| 标准   | 需要设计、集成或影响少量模块的变更                            | 背景与需求、开发任务、Level 0，以及适用的集成验证。    |
| 高风险 | 跨模块、多 Agent 并行、关键数据、安全、迁移或外部不确定性任务 | 完整文档链、上下文包、独立角色、Level 0–3 和严格授权。 |

流程可以按风险简化，但事实真实性、独立审查、设计一致性和外部操作安全不能被省略。

## 使用边界

- 产品目标、业务决策、风险接受和最终授权仍由人类负责；
- Agent 不得替代人类执行未经授权的外部操作；
- 项目可以使用自己的语言、框架、模型和分支策略；
- 大型项目应按 Sprint 拆分，通过多次迭代交付；
- 测试结果必须结合设计审查、系统验证和真实环境验收解释。

## 实践背景与持续演进

这套规范来自真实的 AI 辅助和多 Agent 开发实践。开发过程中发现的问题，会在复盘中被整理为可复用的流程、角色、证据和门禁。

规范会随着实践继续演进。每条新规则都应说明要解决的通用风险，避免把一次事故的处理方式直接固化为普遍要求。规范变更同样需要经过审核，并明确版本、影响范围和传播要求。

## 写在最后

在十多年的软件行业经历中，我先后做过开发者、架构师、项目负责人和部门负责人。一路走来，真正让我始终感到快乐的，还是从零开始，把一个想法逐步变成真实产品的过程，以及最终看到它被创造出来时的成就感。

AI 正在降低软件创造的门槛，让过去需要完整技术团队才能完成的事情，开始有机会被更多人亲自尝试。分享这套规范，是希望把我在多年实践中积累的经验和方法交给更多人，让即使没有技术背景的普通人，也能够借助 AI，从一个想法开始，创造出属于自己的产品，并体会到那份从零到一的快乐。
