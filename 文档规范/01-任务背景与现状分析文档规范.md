# 任务背景与现状分析文档规范

> 规范版本：V2.3
> 规范状态：已审核通过
> 文档定位：开发链路的第一份正式文档  
> 输出目标：形成可信的事实基线和问题定义，不提前承诺具体实现  
> 定稿日期：2026-08-11
> 修订日期：2026-08-15

## 1. 适用场景

以下工作开始前，应先编写背景与现状分析：

- 新功能涉及多个模块、数据表或外部系统；
- 旧功能升级或重构；
- 搜索引擎、数据库、中间件、云服务或第三方接口迁移；
- 当前问题包含性能、容量、一致性或历史技术债；
- 用户提出的是想法或顾虑，尚未形成稳定需求。

## 2. 文档要回答的问题

背景文档必须回答：

1. 谁在什么场景下遇到了什么问题？
2. 当前系统实际如何工作，而不是原本打算如何工作？
3. 代码、数据库、配置和运行环境分别提供了什么证据？
4. 问题影响正确性、体验、性能、成本还是可维护性？
5. 当前有哪些业务、技术、时间、资源和环境约束？
6. 哪些既有设计可以保留？
7. 哪些内容是事实，哪些只是推断或候选方案？
8. 进入需求阶段前，还有哪些问题需要项目负责人确认？
9. 生产运行时实际会激活哪些入口、Scope、并发分支和外部资源？
10. 现有自动化测试替换了哪些真实依赖，因此不能证明什么？

## 3. 输入与调查方式

### 3.1 必须优先读取

- 相关入口、服务、领域模型、基础设施适配器和测试；
- 数据库实体、映射、迁移、SQL 和索引；
- 当前配置结构和运行方式；
- 生产组合根、Host、启动入口、任务调度和运行模式；
- 依赖注入生命周期、工厂、Service Locator、静态状态和共享资源；
- 既有设计文档、历史决策和已知问题；
- 用户提供的日志、截图和真实业务流程。

### 3.2 真实环境调查边界

- 默认只执行只读检查。
- 连接真实数据库、搜索引擎或云服务前，应确认用户授权和环境范围。
- 记录查询时间、环境、数据快照和过滤条件。
- 不得为了“验证”而修改生产数据、索引、配置或任务状态。
- 敏感连接串、密码、Token 和个人信息不得写入文档。

### 3.3 证据等级

| 类型 | 写法要求 |
|---|---|
| 已验证事实 | 给出代码位置、查询结果、日志或官方资料来源 |
| 测量结果 | 记录时间、环境、样本范围和单位 |
| 推断 | 明确写“推断”，并说明依据及不确定性 |
| 建议 | 明确写“候选建议”，不得伪装为已确认需求 |
| 待确认 | 写清由谁决定以及该决定影响什么 |

## 4. 强制章节结构

### 4.1 文档元数据

至少包括：状态、版本、调查范围、数据快照时间、上游资料、审核人和更新时间。

### 4.2 任务背景与业务目标

- 用户或运营流程；
- 当前痛点；
- 为什么现在处理；
- 若不处理的业务影响；
- 理想结果的方向性描述。

本节不可直接写成技术组件清单。

### 4.3 调查范围与排除项

- 检查了哪些项目、模块、数据和环境；
- 哪些内容因权限、环境或时间未检查；
- 本轮只分析、不修改的边界；
- 结论适用的时间范围。

### 4.4 当前系统与数据流

说明：

- 入口和触发方式；
- 模块职责与依赖；
- 数据从哪里产生、转换、存储和消费；
- 主要读路径和写路径；
- 数据真源、缓存、索引和派生数据；
- 外部系统和人工操作点。

除编译时模块关系外，还必须调查运行时激活拓扑：

- 进程、Host、API、Job、命令或其他实际入口；
- 不同运行模式和配置组合会激活哪些组件；
- Singleton、Scoped、Transient 或其他生命周期对象由谁创建和持有；
- 工厂、`IServiceProvider`、反射、插件、`Lazy<T>` 等间接解析路径；
- 并行任务、线程、请求、租户、批次或分区之间共享哪些状态和资源；
- 数据库会话、事务、文件、网络连接和外部客户端的所有权与释放方式。

不使用依赖注入框架的项目也必须用其实际机制表达对象生命周期和资源所有权。

流程复杂时应使用一张最小必要的流程图。

### 4.5 当前数据模型与规模

至少说明：

- 核心实体及关系；
- 主键、业务唯一性和关联方式；
- 关键索引和约束；
- 当前记录量、增长预期和重复倍数；
- 数据质量、空值、重复、孤儿数据等情况；
- 数量是否为精确值、抽样值或估算值。

### 4.6 当前运行与更新机制

按功能实际情况说明：

- 请求、定时、事件、人工或进程结束等触发方式；
- 单次处理、持续运行、全量/增量或其他运行模式；
- 实际存在的并发、失败、重试和恢复方式；
- 日志、告警、健康检查和人工介入；
- 环境和部署限制。

应至少列出本地开发、自动化测试、长期集成、真实外部验证和生产环境之间的关键差异。分支名称、环境名称和基础设施由项目实际配置，不得在通用文档中假定。

### 4.6.1 当前测试能力与证明边界

必须调查现有测试实际覆盖什么，而不是只统计测试数量：

- 哪些测试使用真实生产入口和生产注册；
- 哪些依赖被 Mock、Fake、内存实现或手工构造替换；
- 是否覆盖并发、生命周期、持久化、取消、部分失败和资源释放；
- 哪些测试依赖本地数据库、容器、网络或人工凭据；
- 当前环境不能安全执行哪些测试；
- 现有测试绿色仍无法排除哪些系统风险。

不得以“已有集成测试”这一名称推断其覆盖等级，必须检查实际激活路径和替身边界。

不涉及后台运行或数据更新的功能，不强制编写无关的全量、增量和互斥内容。

### 4.7 问题与风险清单

按优先级组织，推荐：

- `P0`：正确性、数据丢失、安全或生产阻断；
- `P1`：高风险稳定性、性能、容量或一致性；
- `P2`：维护性、扩展性、测试和数据质量；
- `P3`：体验优化或低风险技术债。

每项问题至少包含：

```text
编号与标题
现象
证据
根因或当前推断
影响
触发条件
是否需要本期处理
```

### 4.8 可保留的既有能力

明确哪些代码、表、流程、接口或运营方式可以继续使用，以及保留的理由。背景分析不应只列缺点。

### 4.9 约束与不变量

包括但不限于：

- 不允许破坏的数据结构或兼容性；
- 可用基础设施和成本上限；
- 可接受的一致性延迟；
- 维护窗口和任务运行周期；
- 数据安全和权限；
- 当前迭代明确不处理的重构。
- 允许或禁止自动创建、删除、清空的数据库、Schema、存储卷和外部资源；
- 项目可接受的返工成本与不可接受的环境操作风险；
- 哪些真实环境操作只能由项目负责人人工执行。

### 4.10 候选方向与待确认事项

可以提出候选方向，但必须：

- 分开列出，不与事实混写；
- 说明收益、代价和未解决问题；
- 不在未审核前写成最终架构；
- 列出需要用户逐项判断的问题。

## 5. Codex 执行要求

Codex编写本类文档时应：

1. 先搜索代码和文件，再形成判断。
2. 对关键结论附代码路径、查询证据或日志依据。
3. 对易变化或高风险的外部事实使用官方资料核验。
4. 用真实用户路径解释技术问题的业务影响。
5. 对无法检查的内容明确说明，不补造事实。
6. 发现现状与用户记忆不一致时，以证据说明差异并请用户确认。
7. 不在本阶段直接实施修复，除非用户另行明确授权。
8. 不能把 Context L1 永久上下文、历史上下文包或旧设计直接当作当前事实，必须抽样或逐项核对权威源。
9. 对跨模块任务绘制最小运行时激活路径，并标出仍未验证的交界点。

## 6. 禁止事项

- 只听口述而不检查可用代码和数据；
- 把历史设计文档当作当前运行事实；
- 将一次查询耗时写成正式性能基准；
- 不记录时间和样本范围就引用数据量；
- 在背景阶段锁定尚未审核的技术方案；
- 为追求架构整洁而忽略用户体验或运营现实；
- 混入详细任务拆分、部署步骤或编码承诺。
- 只调查目标文件而不检查其调用者、生产入口和共享资源；
- 用 Mock/Fake 测试结果推断真实生命周期、数据库或外部环境已经验证。

## 7. 审核清单

- [ ] 业务目标和用户场景清晰；
- [ ] 调查范围与未调查范围明确；
- [ ] 当前架构和数据流来自实际代码；
- [ ] 生产入口、运行模式、生命周期、并发和资源所有权已经调查；
- [ ] 当前测试能力、替身和证明缺口已经记录；
- [ ] 核心数据量有时间、环境和口径；
- [ ] 问题按优先级排列且有证据；
- [ ] 事实、推断、建议和待确认项已分开；
- [ ] 可保留能力和不可突破约束已列明；
- [ ] 未进行未经授权的外部修改；
- [ ] 进入需求阶段所需问题已基本回答；
- [ ] 项目负责人已确认背景基线。

## 9. 完成定义

只有在项目负责人确认“事实基线足以支持需求讨论”，运行时拓扑和测试证明边界足够清晰，且关键问题不再依赖未经验证的猜测时，本文件才可标记为“已审核通过”。候选方案无需在背景阶段定稿。
