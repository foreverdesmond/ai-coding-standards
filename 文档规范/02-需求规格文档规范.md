# 需求规格文档规范

> 规范版本：V2.5
> 规范状态：待审核（V2.3 仍为上一已审核基线）
> 文档定位：把已审核的问题和业务目标转化为可验收的系统要求  
> 前置门禁：任务背景与现状分析已审核通过  
> 作者：WorkBuddy（受 Hermes 总调度委派）
> 原定稿日期：2026-08-11
> 修订日期：2026-08-20
> 审核人：Richy（待审）

## 1. 文档目标

需求规格定义“系统必须做到什么”，并成为详细设计、开发范围和最终验收的共同基线。

需求文档不负责决定类名、目录、SDK 调用方式、SQL 细节或具体算法实现；只有当某种技术约束本身属于业务、兼容、安全或平台要求时，才应写入需求。

## 2. 需求编写原则

### 2.1 从用户结果出发

- 先描述用户路径和可感知结果，再描述系统能力。
- 性能指标应关联真实使用场景，不只写“高性能”。
- 架构优雅不能替代业务可用、数据正确和运营可维护。

### 2.2 可验收

每项需求应尽量包含：

- 稳定编号；
- 触发条件；
- 输入或适用范围；
- 必须产生的结果；
- 边界与例外；
- 可观察的验收标准。

避免“尽量”“适当”“快速”“合理”等无法验收的表述。确实无法立即量化时，应写明当前基线、验证方法和由谁在何阶段确定阈值。

### 2.3 明确真源与一致性

涉及派生数据、缓存、搜索索引、消息或多存储系统时，必须明确：

- 哪个系统是数据真源；
- 哪些数据允许冗余；
- 列表和详情分别读哪里；
- 可接受的不一致窗口；
- 冲突时以谁为准；
- 失败时是否允许降级以及如何让调用方感知。

### 2.4 明确范围而非暗示范围

- “本期范围”应列出需要交付的能力。
- “非本期范围”应列出容易被误认为包含的内容。
- 文档为未来接口或模块提供设计输入时，必须明确它不等于本期开发授权。
- 旧系统清理、全局重构、多语言、API 改造、部署上线等常见扩展项都应显式判断是否入期。

### 2.5 验收层级必须可决策

- 每项关键需求必须说明由 Level 0、1、2、3 中哪些层级证明；等级定义引用 `08-开发验证、代码审查与合并门禁规范.md`。
- 需求必须区分自动化可证明部分、生产形态系统验证和真实外部环境验证。
- 每个 `NotRun` 项必须说明阻塞任务验收、长期集成分支、稳定分支还是仅阻塞发布。
- 无法安全提供测试数据库、外部账户或破坏性操作权限时，应定义人工验证、风险接受或不适用理由，不得把危险环境操作变成默认验收前提。

## 3. 强制章节结构

### 3.1 文档元数据与上游基线

至少包括：状态、版本、背景文档版本、目标平台或版本、数据基线、审核人和更新时间。

### 3.2 文档目的

说明本文解决什么问题、约束哪些后续文档，以及不承担什么职责。

### 3.3 用户目标、核心路径与成功标准

至少描述：

- 核心用户是谁；
- 用户从哪里进入；
- 关键操作顺序；
- 第一屏或核心响应必须提供什么；
- 点击、展开或后续动作如何继续；
- 用户可感知的速度、准确性和故障表现。

### 3.4 背景约束摘要

只引用已审核背景中的关键事实：现有数据结构、规模、平台限制、成本、运行窗口、兼容要求和本期不能改动的部分。不要重复整份背景文档。

### 3.5 已确认的业务与架构边界

记录已经影响需求范围的高层决定，例如：

- 文档或数据粒度；
- 业务身份与唯一性；
- 系统职责分工；
- 读写边界；
- 允许的最终一致性；
- 未来扩展的兼容边界。

这些内容是需求级约束，不展开实现细节。

### 3.6 范围与非范围

分别列出：

- 本期必须交付；
- 本期明确不做；
- 只作为未来设计输入的内容；
- 依赖其他迭代或人工阶段完成的内容。

### 3.7 术语与业务口径

必须定义可能产生歧义的：

- 实体身份、状态和时间；
- 有效记录或可参与计算的条件；
- 排序、聚合、折扣、价格等公式；
- 空值、零值、缺货、停用、删除等语义；
- 相同值时的确定性选择规则；
- 时间是否使用 UTC、时区如何展示。

### 3.8 功能需求

使用 `FR-001` 等稳定编号。每项建议使用以下格式：

```markdown
### FR-001：<名称>

**目标**：

**规则**：
- 系统必须……
- 系统不得……

**边界与异常**：

**验收标准**：
```

### 3.9 专项流程需求

当功能包含同步、导入、迁移、批处理、全量构建、增量处理或任务调度时，应单独编号并说明：

- 触发方式；
- 输入范围；
- 并发与互斥；
- 成功、部分成功、失败、超时和取消；
- 重试、恢复和幂等；
- 已处理数据如何确认；
- 允许的延迟与新鲜度目标。

### 3.10 非功能需求

使用 `NFR-001` 等编号，至少评估：

- 性能与响应时间；
- 容量与增长；
- 可用性与恢复；
- 一致性与数据完整性；
- 安全、权限和秘密管理；
- 可观测性；
- 兼容性；
- 可测试性；
- SOLID 与模块边界。

没有现成测试环境时，不得删除相关要求；应把环境测试作为后续人工验收，并明确它阻塞哪个阶段、由谁执行、需要什么授权。

### 3.11 平台与外部限制

列出具体版本、免费额度、协议、连接、安全和容量限制。易变化的信息应引用官方来源和核验日期。

### 3.12 迁移与兼容要求

明确：

- 是否与旧功能并行；
- 是否需要影子运行或双读对比；
- 现有数据结构是否保持不变；
- 回退时用户和数据会发生什么；
- 哪些清理工作暂缓。

### 3.13 验收清单

验收清单应覆盖结构、业务功能、同步/迁移、异常、性能、安全和 SOLID 边界。每项应能被自动化测试、静态检查或人工环境验证证明。

每项关键验收至少记录：

| 字段 | 含义 |
|---|---|
| 验收编号 | 稳定编号，如 `AC-001` |
| 关联需求 | `FR/NFR` 编号 |
| 验收层级 | Level 0/1/2/3，可多选 |
| 环境与数据 | 最小必要环境、配置和样本 |
| 执行责任 | 开发者、Reviewer、系统 Reviewer、项目负责人等角色 |
| 自动化程度 | 自动、半自动、人工 |
| 阻塞阶段 | 任务、长期集成分支、稳定分支或发布 |
| 成功证据 | 测试、日志、指标、截图、数据核对等 |
| NotRun 规则 | 原因、风险、后续责任人与例外批准人 |

验收层级描述业务风险需要在哪个阶段被证明，不应在需求中写死具体测试类名、脚本或工具。

### 3.13.1 分支与环境策略引用

需求文档应引用项目在开发任务文档中配置的逻辑分支角色，但不写死实际分支名称。默认语义为：

- Level 0 阻塞单任务进入迭代开发分支；
- Level 1 阻塞迭代进入长期集成分支；
- Level 2 在长期集成分支进行生产形态系统验证；
- Level 3 和最终合并审核阻塞进入稳定分支。

项目负责人可以批准不同映射，但必须记录理由、风险和替代门禁。

### 3.14 已审核决定与待审核项

- 已确认决定按序号记录结论和影响范围。
- 待审核项使用复选框，逐项由项目负责人确认。
- 待审核项清零前不得将文档整体设为“已审核通过”。

## 4. 需求与实现的边界

需求可以规定：

- 必须使用某个兼容平台或协议版本；
- 必须保持某个数据库结构不变；
- 必须支持某种用户可见能力或运行模式；
- 必须在一定容量和延迟下工作；
- 必须遵循权限边界或 SOLID。

需求通常不应规定：

- 类、接口、方法和目录的具体名称；
- 每批固定多少条、每页固定多大；
- 具体 SQL、DSL 或 JSON mapping；
- 使用哪个内部设计模式；
- 开发任务由哪个文件先改。

若项目负责人已经明确指定某项实现限制，应将其写成“已确认技术约束”，并在详细设计中展开。

## 5. 追溯要求

需求文档应维护最小追溯关系：

| 需求编号 | 来源问题/目标 | 验收方式 | 状态 |
|---|---|---|---|
| FR-001 | ISSUE-001 | 自动化测试/人工验证 | 待审核 |

复杂项目可在详细设计中扩展为“需求 → 设计章节 → 开发任务 → 测试证据”。

## 6. 执行 Agent（WorkBuddy/Codex）执行要求

1. 只以已审核背景为事实基线。
2. 通过对话帮助用户识别遗漏的业务规则和异常边界。
3. 对重要取舍给出候选方案、收益和代价，由用户决定。
4. 用户逐项确认后立即更新决定和审核状态。
5. 主动识别范围扩张并把它放入非本期范围或待决项。
6. 不因技术实现方便而改变用户可见行为。
7. 完成每轮更新后列出仍需审核的事项。
8. 协助项目负责人判断每项验收应由哪个层级证明，但不把技术测试细节写成业务需求。
9. 发现某项验收需要危险或不可用环境操作时，提供安全替代、人工验证和风险接受方案。

## 7. 禁止事项

- 没有背景基线就直接编写大规模需求；
- 把候选方案写成已确认要求；
- 用技术名词掩盖不明确的业务口径；
- 只写正常路径，不写无数据、失败、超时和部分成功；
- 把 API 未来设计讨论误写为本期 API 开发范围；
- 把部署、上线或真实环境操作加入功能需求交付范围；
- 只写“自动化测试/人工验证”而不说明层级、阻塞阶段和责任人；
- 把建立、删除或清空真实数据库等高风险操作默认为验收条件；
- 需求审核通过后在详细设计中静默改变它。

## 8. 审核清单

- [ ] 用户目标和核心路径完整；
- [ ] 本期范围、非范围和未来输入边界明确；
- [ ] 数据真源和一致性边界明确；
- [ ] 业务术语、公式、过滤和排序规则无歧义；
- [ ] 功能需求均有编号且可验收；
- [ ] 关键验收均已指定 Level 0–3、责任人、阻塞阶段和成功证据；
- [ ] `NotRun` 的风险、后续责任和例外批准规则明确；
- [ ] 同步、迁移或批处理的异常语义完整；
- [ ] 性能、容量、安全、可观测性和兼容要求明确；
- [ ] 迁移、并行和回退要求明确；
- [ ] 每项需求可追溯到背景目标或问题；
- [ ] 所有重要决定由项目负责人确认；
- [ ] 待审核项为零。

## 10. 完成定义

需求文档只有在范围、口径、异常边界、验收层级、阻塞阶段和责任人均已明确，所有待审核项已经项目负责人确认后，才可标记为“已审核通过”并作为详细设计基线。
