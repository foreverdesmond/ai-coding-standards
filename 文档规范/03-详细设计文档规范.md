# 详细设计文档规范

> 规范版本：V2.3
> 规范状态：已审核通过
> 文档定位：将已审核需求转化为可实现、可测试的技术方案  
> 前置门禁：需求规格已整体审核通过  
> 适用范围：API、爬虫、后台任务、数据处理、搜索、迁移、前端及其他功能开发  
> 定稿日期：2026-08-11
> 修订日期：2026-08-15

## 1. 文档目标

详细设计必须让开发者不依赖聊天记忆即可正确实现功能，也必须让审查者能够判断方案是否满足需求、架构原则、可靠性、安全性和可测试性要求。

详细设计由两部分组成：

1. **通用设计骨架**：任何功能都必须覆盖；
2. **专项设计模块**：根据功能类型和风险按需选择。

不适用的专项模块不应强行写入正文。若某项看似相关但最终不适用，应简要标记 `N/A` 并说明理由。

## 2. 需求与设计的边界

### 2.1 需求文档负责什么

需求文档负责确定：

- 用户或业务需要什么结果；
- 业务术语、规则和验收口径；
- 本期范围与非本期范围；
- 性能、安全、兼容性等外部约束；
- 哪些重要取舍已经获得项目负责人确认。

### 2.2 详细设计负责什么

详细设计负责确定：

- 现有系统中由哪些组件实现需求；
- 组件之间如何协作；
- 数据和控制如何流动；
- 接口、模型和外部依赖如何组织；
- 正常、异常和边界情况如何实现；
- 如何测试和证明实现正确。

详细设计可以引用业务规则，但不应重新发明或修改业务规则。发现需求存在歧义时，应回到需求文档处理，而不是在设计中静默作出业务决定。

## 3. 设计前的功能分类

编写详细设计前，先判断本次功能涉及哪些类型。一个功能可以同时属于多个类型。

| 功能类型 | 典型例子 | 通常需要选择的专项模块 |
|---|---|---|
| API 查询 | 商品列表、详情、搜索接口 | API、查询与缓存、性能、安全 |
| API 写入 | 创建、修改、删除、状态变更 | API、事务与并发、幂等、安全 |
| 爬虫/数据采集 | 超市商品和价格爬取 | 爬虫、外部集成、调度、数据质量 |
| 后台任务 | 定时清理、同步、统计、通知 | Job、状态与恢复、可观测性 |
| 数据迁移/同步 | 数据库迁移、搜索索引重建 | 数据处理、全量/增量、校验与切换 |
| 搜索功能 | 全文检索、建议、高亮、排序 | 搜索与索引、查询、容量 |
| 领域规则 | 定价、折扣、资格判断 | 业务规则实现、精度与确定性 |
| 前端/UI | 页面、组件、交互流程 | UI 状态、交互、可访问性、接口契约 |
| 外部服务集成 | 支付、地图、AI、邮件 | 外部契约、限流、失败与降级 |
| 基础设施 | 日志、JobHost、缓存、存储适配器 | 模块边界、配置、安全、兼容性 |

文档首页应列出本次选择的功能类型和专项模块，使审核者知道哪些内容必须检查、哪些内容明确不适用。

## 4. 所有功能必须覆盖的通用设计骨架

### 4.1 文档元数据

至少包括：

- 文档状态和版本；
- 已审核需求文档及版本；
- 本次功能类型；
- 选择的专项设计模块；
- 负责人、审核人和最后更新时间；
- 目标运行环境或兼容版本（如适用）。

### 4.2 设计目标与结论

用简洁文字说明：

- 本设计准备解决什么；
- 最终选择的总体实现方式；
- 最关键的组件和边界；
- 对现有系统的主要影响；
- 本设计明确不处理什么。

### 4.3 需求追溯

每个已审核需求都必须有设计落点：

| 需求编号 | 设计落点 | 验证方式 | 状态 |
|---|---|---|---|
| FR-001 | 5.2、6.1 | 单元测试、接口测试 | 已覆盖 |

如果某需求不需要代码变化，也应说明由现有能力满足的证据。

### 4.4 系统上下文与影响范围

说明：

- 功能从哪里被触发；
- 谁调用它，它又依赖谁；
- 输入从哪里来，输出到哪里去；
- 会修改哪些项目、模块或数据；
- 哪些现有接口和行为必须保持兼容；
- 哪些相邻系统不在本次范围。

只有当关系较复杂时才使用架构图、流程图或时序图，不为简单功能制造图表。

### 4.5 组件职责与依赖方向

对新增或变化的组件说明：

- 单一职责；
- 对外提供的能力；
- 依赖的抽象；
- 外部技术细节的适配位置；
- 项目和目录落位；
- 运行时调用方向；
- 编译时引用方向。

运行时调用方向与编译时依赖方向必须分开描述，不能用一条笼统的分层箭头替代。

### 4.5.1 运行时激活、生命周期与资源所有权

涉及依赖注入、并发、后台执行、持久化、外部客户端或可变状态时，必须给出运行时激活路径，而不能只画项目引用关系。

至少记录：

| 对象或资源 | 创建入口 | 生命周期/作用域 | 是否可变或线程安全 | 并发调用者 | 所有者与释放责任 |
|---|---|---|---|---|---|

设计必须检查：

- 长生命周期对象是否直接或间接持有短生命周期对象；
- 工厂、Service Locator、反射、插件、`Lazy<T>`、回调和静态字段是否隐藏真实依赖；
- 请求、任务、租户、批次、分区或其他并行单元是否需要独立 Scope；
- 数据库会话、事务、Writer、Stream、锁、缓存和外部客户端能否被并发共享；
- 资源由谁创建、提交、回滚、取消、释放，异常路径是否一致；
- 运行模式或配置组合是否改变对象图和并行关系。

不使用 DI 框架的项目仍须按实际对象创建机制完成本节。

### 4.6 核心接口、模型与契约

只设计本功能实际需要新增或变化的内容：

- 输入、输出和返回状态；
- 必填、可选、默认值与校验；
- 取消、超时和错误语义；
- 模型所属层级；
- 版本和兼容方式；
- 是否允许外部 SDK 类型穿透边界。

数据库实体、领域模型、应用 DTO、API 契约和外部系统模型不是同一概念，应按职责分别放置。

### 4.7 主要执行流程

至少描述：

- 主成功路径；
- 关键分支；
- 无数据或空结果；
- 输入无效；
- 依赖失败；
- 取消和超时；
- 必要的恢复或降级。

简单同步调用可用步骤说明；存在多个组件、异步状态或循环处理时再使用时序图或状态机。

### 4.8 错误处理与可靠性

根据功能风险定义：

- 错误分类；
- 哪些错误向调用方返回；
- 哪些错误可以重试；
- 重试次数、退避和停止条件；
- 部分成功如何表达；
- 是否需要幂等、补偿或恢复；
- 降级行为是否会掩盖真实故障。

不是所有功能都需要复杂状态机，但所有功能都必须明确失败时会发生什么。

还必须定义异常所有权：哪一层捕获、转换、记录和决定运行状态。空 `catch`、仅记录后继续、返回空集合或默认成功等容错行为，必须有批准的业务语义、可观测性和测试，不得作为避免失败的默认写法。

### 4.9 配置与安全

说明适用内容：

- 配置项、默认值和启动校验；
- 环境差异；
- 认证与授权；
- 输入验证和输出保护；
- 密码、Token 和连接信息的来源；
- 日志中的敏感信息保护；
- 网络协议和最小权限。

秘密不得进入代码、普通配置示例或设计文档。

### 4.10 可观测性

说明如何判断功能是否正常：

- 关键结构化日志；
- 成功、失败和耗时指标；
- 必要的业务计数或进度；
- 健康状态或诊断入口；
- 关联一次请求或任务的标识；
- 哪些内容不得记录。

观测内容应与功能类型匹配。普通 API 不需要批处理游标，简单工具也不必设计完整监控平台。

### 4.11 性能与资源影响

根据需求说明：

- 主要性能路径；
- 预期数据量、请求量或任务频率；
- CPU、内存、网络、数据库或外部服务影响；
- 缓存、分页、并发或批量参数；
- 参数依据和后续调优方式。

低风险功能可以简要说明“无显著新增资源消耗”及判断依据。关键参数不能无依据写死。

### 4.12 测试设计

按适用范围规划：

- 单元测试；
- 接口或契约测试；
- 组件集成测试；
- 端到端测试；
- 性能和容量测试；
- 安全测试；
- 后续人工环境验证。

测试环境不可用时必须记录 `NotRun`、原因、责任人和后续验证方式，不得声称已经通过。

涉及数据库、持久化、真实外部系统或生产形态入口时，还必须设计安全验证路径：

- 明确哪些验证可以在任务分支离线执行，哪些只能在迭代候选或真实环境执行；
- 优先提供无网络、只读、Fake、可回滚或不会到达写入点的验证入口，同时如实说明其证明边界；
- 没有隔离测试库时，不得把真实写库作为开发者或 Reviewer 的默认验收手段；
- 需要项目负责人手工启动、观察并及时停止时，必须给出停止点、预计首次副作用发生点、日志判据和剩余风险；
- 开发、Review、集成和真实环境验收分别由哪个任务或角色承担必须明确。

测试设计必须引用需求中的 Level 0–3 验收映射，并对每个替身说明证明边界：

| 测试或层级 | 真实路径 | 被替换依赖 | 能证明 | 不能证明 |
|---|---|---|---|---|

单元、Mock、Fake 或内存测试不能单独证明生产对象图、真实并发资源、数据库 Provider 行为或真实外部系统正确。设计应把剩余风险放到合适层级，而不是隐去。

#### 4.12.1 生产组合根风险评估

新增或修改生产注册、服务生命周期、关键配置契约、Host/启动入口或运行时关键入口激活时，必须评估并规划生产组合根集成测试。仅增加尚未接线的组件、测试专用代码或不影响生产对象图的局部构造调整，不自动触发完整组合根测试。

测试设计必须明确：

- 使用与生产相同的服务注册扩展或 Host 构建路径，不在测试中另写一套等价注册；
- 在有效的最小配置下，逐个解析所有受影响的关键入口服务；适用时同时启用 `ValidateOnBuild` 和 `ValidateScopes`；
- 若服务在 Host 启动或首次运行时才被激活，测试必须覆盖对应激活点，不能只验证容器能够创建；
- 启动配置校验、Options 的 `ValidateOnStart`、手工 `new` 组件或使用 Mock 绕过容器，只能作为补充测试，不能作为生产依赖图可解析的充分证据；
- 对以下常见接线错误给出检查口径：`IOptions<T>`、`IOptionsSnapshot<T>`、`IOptionsMonitor<T>` 与直接注入 `T` 是否和实际注册一致；命名 Options 的名称和消费方式是否匹配；Singleton、Scoped、Transient 的依赖方向及 Scope 是否有效；开放泛型能否闭合并解析；工厂注册能否用生产参数创建目标服务，且其返回类型、生命周期和内部依赖正确；
- 对 Service Locator、工厂、`Lazy<T>`、静态缓存和回调中的间接解析执行实际激活与并发检查，不能仅依赖容器静态校验；
- 测试宿主若缺少日志、数据库、时钟或外部服务，可使用明确的测试替身、测试容器或无网络配置，但不得替换或绕过本次被审查的生产注册路径；测试结果必须区分“测试宿主缺少必要配套”与“生产 DI 注册或依赖图缺陷”；
- 证据至少包含测试名称、真实注册入口、解析的关键服务清单、配置环境或替身说明、执行命令和结果。

反例：Options 绑定与校验测试通过、组件也能被手工构造，不代表生产容器能够激活消费该组件的关键入口服务。若消费者请求的类型、名称或生命周期与组合根实际注册不一致，必须由生产组合根集成测试在开发阶段发现。

### 4.13 兼容、迁移与回退

所有功能都应判断是否需要这一节：

- 没有兼容或迁移影响时，写明 `N/A` 和理由；
- 修改现有接口、数据、配置或运行方式时，说明升级顺序；
- 需要并行、灰度、数据转换或回退时，选择相应专项模块展开；
- 清理旧代码或旧资源的时点必须明确。

### 4.14 设计决定、风险与待审核项

记录：

- 主要候选方案；
- 最终选择和理由；
- 被拒绝方案；
- 仍然存在的风险；
- 需要项目负责人决定的冲突；
- 非本期范围。

每项剩余风险还必须说明在哪个 Level 验证、阻塞哪个分支角色或发布阶段、环境不足时由谁接受风险。

重要决定使用 `DEC-001`；SOLID 冲突可使用 `SOLID-DEC-001`。

## 5. SOLID 强制约束

所有详细设计必须逐项审核，但审查内容应结合当前功能，而非机械套用接口数量。

| 原则 | 必须回答的问题 |
|---|---|
| S：单一职责 | 新增组件是否只有一个主要变化原因？ |
| O：开闭原则 | 合理的新实现能否通过扩展完成，还是每次都要修改稳定核心？ |
| L：里氏替换 | 同一抽象的实现是否保持一致的输入、输出、错误和取消语义？ |
| I：接口隔离 | 调用方是否只依赖实际使用的最小能力？ |
| D：依赖倒置 | 核心规则是否依赖抽象，外部技术细节是否位于边界之外？ |

必须写出与本次功能有关的具体结论。旧代码可以暂不重构，但新代码不得无理由复制其违规设计。

发生冲突时：

```markdown
### SOLID-DEC-001：<冲突标题>

- 冲突：
- 方案 A：
- 方案 B：
- 影响：
- 推荐：
- 项目负责人决定：待审核
```

## 6. 专项设计模块

以下模块是设计问题清单，不是每份详细设计的固定章节。只选择与当前功能有关的模块。

### 6.1 API 与服务接口

适用于查询或写入 API：

- 路由、方法和版本；
- 请求、响应和错误契约；
- 参数校验；
- 认证、授权和数据范围；
- 分页、排序、过滤和缓存；
- 写入幂等、并发更新和冲突；
- 限流、超时和兼容性。

### 6.2 爬虫与数据采集

适用于爬虫和外部数据获取：

- 数据源、入口页面和抓取范围；
- 调度频率和启动方式；
- 请求限速、并发、超时和重试；
- 页面或接口解析边界；
- 数据清洗、去重和身份判断；
- 增量发现、检查点和断点恢复；
- 数据质量验证；
- 来源变化、封禁或部分失败处理；
- 合规、服务条款和敏感信息边界。

### 6.3 后台任务与 Job

适用于定时或手工后台任务：

- 触发和参数；
- 单次运行或常驻运行；
- 重入、互斥和并发范围；
- 最大运行时间、取消和进程退出；
- 运行状态、进度和恢复；
- 异常捕获和退出码；
- 调度器与业务服务的职责边界。

### 6.4 数据存储与持久化

仅在功能新增或改变数据持久化时选择：

- 表、列、关系和约束；
- 主键、业务键和唯一性；
- 事务边界和隔离；
- 索引与查询计划；
- 数据生命周期、删除和审计；
- 数据库脚本的幂等性和升级顺序。

### 6.5 数据处理、同步与迁移

仅适用于派生数据、导入、同步或迁移：

- 来源、目标和数据真源；
- 转换、过滤、聚合和校验；
- 变化捕获；
- 全量、增量和补偿；
- 并发、幂等和结果未知；
- 切换、回滚和旧数据清理；
- 对账和一致性窗口。

### 6.6 搜索与索引

仅适用于全文检索或搜索存储：

- 文档粒度和文档身份；
- mapping、analyzer 和字段用途；
- 查询、过滤、排序、高亮和建议；
- 分页与相关性；
- 索引生命周期和 alias；
- 容量、分片和批量写入。

### 6.7 查询、缓存与读取优化

适用于读密集功能：

- 查询形态和返回粒度；
- 数据加载和 N+1 风险；
- 索引、缓存和失效；
- 分页和大结果集；
- 一致性与陈旧数据；
- 热点和降级。

### 6.8 领域规则与计算

适用于复杂业务计算：

- 输入和前置条件；
- 规则执行顺序；
- 精度、舍入和单位；
- 相同值的确定性选择；
- 时间与时区；
- 规则扩展方式；
- 可单元测试的纯计算边界。

业务规则本身必须来自需求文档，本模块只说明其技术实现。

### 6.9 事务、并发与一致性

只在存在共享写入或多步骤状态变化时重点展开：

- 事务边界；
- 乐观或悲观并发；
- 锁、租约和唯一约束；
- 重复请求和幂等键；
- 多存储一致性；
- 补偿和最终一致性。

### 6.10 外部系统集成

- 外部契约和版本；
- 客户端职责；
- 认证和连接；
- 限流、重试和熔断；
- 错误映射；
- 模拟、契约测试和不可用时的行为；
- 外部 SDK 与核心代码的隔离。

### 6.11 前端与交互

- 页面或组件职责；
- 用户交互和状态变化；
- 加载、空、错误和重试状态；
- 表单校验；
- 响应式布局和可访问性；
- 客户端缓存与状态管理；
- API 契约和兼容性。

## 7. 专项模块选择规则

### 7.1 必须选择的情况

- 该维度直接承接一项需求；
- 该维度会新增或修改代码、表、配置或外部资源；
- 该维度包含明显正确性、安全、性能或运维风险；
- 不说明会导致不同开发者作出不兼容实现。

### 7.2 可以不选择的情况

- 本功能完全不涉及该维度；
- 现有设计原样复用且有明确引用；
- 只是远期想法，不在当前范围。

### 7.3 禁止的做法

- 因模板存在就强行设计无关的数据库、消息、缓存或索引；
- 把所有可选模块写成空标题；
- 用 `N/A` 跳过实际存在的高风险问题；
- 把某次迁移项目的具体技术方案提升为全项目通用规则。

## 8. Codex 执行要求

1. 开始前确认需求版本和整体审核状态。
2. 检查现有代码分层、入口和依赖，不凭空设计项目结构。
3. 先完成“功能分类与专项模块选择”，再展开正文。
4. 对简单功能保持设计简洁，对高风险功能展开必要细节。
5. 对关键方案比较主要替代项，不为显而易见的小实现制造形式主义。
6. 主动执行 SOLID 审核，但不把 SOLID 等同于项目数量越多越好。
7. 外部平台事实使用目标版本的官方资料。
8. 发现需要改变业务规则或范围时，回到需求阶段请求裁决。
9. 每轮更新后列出新增决定、已选模块和剩余待审核项。

## 11. 不同功能的最小示例

### 11.1 API 查询更新

建议选择：API 与服务接口、查询与缓存、事务并发（有写入时）、安全、性能。

通常不需要：爬虫、搜索索引、全量/增量迁移。

### 11.2 爬虫功能

建议选择：爬虫与数据采集、后台任务、外部系统集成、数据持久化、数据质量、可观测性。

通常不需要：API 路由、搜索 mapping、alias 切换。

### 11.3 搜索引擎迁移

建议选择：数据处理与迁移、搜索与索引、后台任务、外部系统集成、事务并发、校验和回退。

### 11.4 简单领域规则修改

建议选择：领域规则与计算、受影响接口或模型、单元测试、兼容性。

通常不需要：复杂架构图、运行状态表、迁移流程或容量模型。

## 12. 完成定义

详细设计只有在与所选开发路线相称的设计内容完整、所有需求有设计落点、运行时生命周期与资源所有权清晰、异常所有权明确、测试替身证明边界和 Level 0–3 验证落点可执行、生产组合根测试已按风险规划、SOLID 五项已经判断且冲突已裁决、待审核项清零后，才可标记为“已审核通过”。
