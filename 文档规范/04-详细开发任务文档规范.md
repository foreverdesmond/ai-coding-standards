## 2. 开发路线选择

项目应从以下三条路线中选择。路线由失败后果、影响范围、可逆性、并发复杂度、数据或安全风险、外部不确定性、可观测性和测试缺口共同决定，不能只按代码行数或技术类别判断。

### 2.1 轻量路线

适用于局部、可逆、影响面小且自动化充分的修改，例如简单缺陷、纯逻辑或低风险配置调整。

最低制品：

- 一份任务简报，可直接记录在 Issue、任务文档或批准的等价载体中；
- 目标、范围、风险、验证和回退说明；
- 开发者自检和独立第二视角 Review；
- 不强制独立 Context L2，也不强制创建完整四文档链。

### 2.2 标准路线

适用于单模块或少量模块、风险可控但需要明确设计和集成验证的开发。

可以把背景、需求、设计和任务合并为一份结构完整的开发说明，但必须保留各阶段的核心问题、SOLID 审查、测试层级和批准状态。

Context L2 按 `06` 的触发条件决定是否生成。

### 2.3 高风险路线

适用于跨模块、多 Agent、长周期、复杂并发、生产入口、关键持久化、迁移、安全、不可逆操作、外部协议或测试缺口明显的任务。

使用完整文档链、正式任务图、独立 Context L2、明确的系统集成任务和 Level 0–3 验证计划。

### 2.4 路线升级与降级

- 项目可以预先批准默认路线和风险阈值，避免每个小任务重复审批；
- 发现影响面扩大、假设失效或高风险交界后必须升级路线；
- 降级必须记录依据，不能由开发者为了减少门禁自行决定；
- 路线简化不豁免需求一致性、SOLID、证据真实性和外部操作安全。

## 3. 探索任务

当关键事实尚不足以完成需求或设计时，可以先建立技术 Spike 或探索任务：

- 默认只读，或在隔离环境中执行；
- 不产生可直接合并的正式功能代码；若产生实验代码，应明确丢弃或重新进入正式开发流程；
- 输出事实、限制、风险、候选方案和仍未知内容；
- 不得借探索任务绕过需求、设计或外部操作授权；
- 探索结论写回背景或设计后，再决定正式开发路线。

## 5. 任务拆分原则

### 5.1 原子性

一个任务应有一个清晰目标和一组高度相关的改动，能够在一次开发—Review 闭环中完成。若同时包含多个独立状态机、外部系统或不相关重构，应继续拆分。

不要过度拆分只产生空文件或无独立行为的任务。

任务必须先按职责分类，不得用同一任务同时表示编码、迭代合并、集成验证和主分支合并：

| TaskType | 职责 | 典型交付 |
|---|---|---|
| CodingTask | 独立编码、定向验证并提交任务分支 | `CodeBaseSHA..HeadSHA` |
| ReworkTask | 在原任务分支关闭 Review Findings | 新 `HeadSHA` |
| IterationMergeTask | 合并准确的已审核任务提交到迭代分支，或按已通过门禁提升非主分支候选 | `Integrated`/候选提升提交 |
| IntegrationValidationTask | 在迭代候选上执行 Level 1/系统验证 | `IntegrationVerified` 或 Findings |
| MainMergeTask | 在最终门禁和授权后合并准确候选到主分支 | `Merged` 提交 |
| DocumentationTask | 更新规范、设计、证据或上下文 | 文档审核目标 |

`IterationMergeTask`、`IntegrationValidationTask` 和 `MainMergeTask` 不得夹带新的业务实现。发现需要改代码时，必须回到原 CodingTask/ReworkTask 或建立新的修复任务。

### 5.2 依赖与持续集成

- 先稳定真正共享的契约，再实现依赖它的任务；
- 每条依赖必须标明类型：`Code`、`Review`、`Integration`、`Validation` 或 `Evidence`；
- 下游不得把尚未 Review 的实现当作正式基线；需要实际使用上游代码的下游任务默认依赖 `Integrated`，只消费稳定契约且不需要实现时才可依赖 `TaskAccepted`；
- 同一任务的前置验证和集成后复验必须使用不同 ID 或明确子阶段，例如 `DEV-008A` 与 `DEV-008B`，不得复用同一状态造成循环依赖；
- **依赖图环检测**：Hermes 在建台账登记任务依赖时执行依赖图（DAG）校验；检测到环依赖（A↔B 互等满足）则**拒绝登记该任务并升级项目负责人（Richy）**，不得静默登记导致任务永远达不到 `Ready`。长期 `Ready`/`InProgress` 无进展的停滞检测与升级见 `09` §11.1；
- 每个已接受任务由独立 `IterationMergeTask` 合入迭代候选后，应运行受影响的持续集成检查；
- 正式 Level 1 仍在冻结候选上形成版本结论，但不能等到迭代末尾才第一次集成。

### 5.3 修改授权与文件所有权

- 默认按职责、模块或行为边界授权，允许修改直接相关的测试和局部接线；
- 并行冲突、共享入口、敏感资源和高风险任务才要求精确文件清单；
- 只读调查范围应覆盖调用者、生产入口、注册、配置、测试和相邻模块；
- 超出职责边界的修改必须先上报；
- 用户已有改动和无关未跟踪文件必须保留。

#### 5.3.1 分支、worktree 与 Git 权限

- 每个真实 `CodingTask` 必须有唯一任务分支和独立 worktree；worktree 只是工作目录，分支是任务归属，commit SHA 是审核身份；
- 开发者和返工执行者只能向自己的任务分支创建本地 commit，不得直接提交或合并到迭代开发分支、长期集成分支、稳定分支或主分支；
- Coding Reviewer、系统 Reviewer 和最终合并 Reviewer 均为只读角色，不得通过修改候选来使其通过；
- 只有独立 `IterationMergeTask` 可以把准确的 `TaskAccepted` 提交合入迭代开发分支；
- 只有独立 `MainMergeTask` 可以在 `MergeApproved` 和项目负责人明确授权后把精确候选合入主分支；
- 返工继续使用原任务分支并产生新 commit；新 `HeadSHA` 自动使旧 Review 结论失效。

### 5.4 跨任务系统集成责任

涉及多任务或关键端到端路径时，必须指定一个系统集成责任任务或责任人，防止所有局部任务通过后仍无人验证组合行为。

按风险覆盖：

- 生产入口和组合根；
- 跨任务接口与配置；
- 生命周期、Scope、并发与共享资源；
- 错误传播、运行状态和部分失败；
- 持久化或外部边界；
- 持续集成检查和正式 Level 1 证据。

单一局部任务不存在真实交界时可标记 `N/A`。

## 6. 风险评级

推荐 `Low / Medium / High`，判断依据包括：

- 失败后果和影响范围；
- 修改的可逆性和回退难度；
- 数据破坏、安全或权限风险；
- 并发、时序和状态复杂度；
- 外部依赖的不确定性；
- 可观测性和故障发现速度；
- 自动化测试与真实环境之间的证明缺口。

DI、Host、持久化、外部服务等技术类别只能触发风险评估，不能单独决定为 `High`。

风险评级决定开发路线、Context L2、Review 能力和验证深度。

## 7. 单任务契约

每项正式开发任务至少包含以下内容；轻量路线可以用紧凑表格表达。

### 7.1 标识与基线

- 稳定 ID、名称、`TaskType`、路线和风险等级；
- 来源需求、设计决定和验收项；
- `InvocationID`、预期执行机制和执行角色；
- `TaskBranch`、`WorktreePath`、`CodeBaseSHA`、预期 `ReviewedCommitRange`/`ReviewedCommitSet` 和 `MergeTarget`；纯文档或经批准例外可以使用不可歧义文档目标；
- `RequirementsBaselineRef`、`DesignBaselineRef`、`TaskDocumentBaselineRef` 和适用的 `ContextBaselineRef`；文档基线不得只引用另一个可变工作区路径；
- 依赖任务、`DependencyType`、要求达到的状态和并行条件；
- Context L2 路径，或 `N/A` 及触发判断。

### 7.2 目标与范围

- 一句话目标和用户/系统结果；
- 允许修改的职责、模块或精确文件；
- 必须自主调查的只读范围；
- 明确禁止的行为和外部操作；
- 非本任务内容。

### 7.3 实现和验证责任

- 必须交付的行为、接口、配置或脚本；
- 正常、边界、失败、取消和兼容要求；
- 本任务负责的 Level 0–3 证据；
- 适用的生产入口、生命周期和资源风险；
- `NotRun`、环境限制和后续责任人。
- 外部副作用风险 `ExternalSideEffectRisk` 及安全验证方法 `SafeValidationMethod`；
- 任务分支上的定向验证、迭代分支上的集成验证和负责人手工验证各自由谁承担。

任何可能造成数据库、索引、存储或真实外部状态变化的验证，都不得由 `CodingTask`、`ReworkTask`、Reviewer 或合并任务执行；必须拆为独立 `IntegrationValidationTask`/外部验证任务，并记录项目负责人授权和执行主体。

### 7.4 SOLID 硬门禁

每个任务都必须接受 SOLID 判断：

- S：职责和变化原因是否清晰；
- O：扩展是否避免无必要修改稳定核心；
- L：同一抽象的行为、错误和取消语义是否可替换；
- I：调用方是否只依赖需要的能力；
- D：核心逻辑是否依赖抽象，技术细节是否位于边界。

低风险任务可以提交一条简洁的“无实质风险”结论，但 Reviewer 仍须完成判断。高风险、出现取舍或发现违规时必须逐项展开证据。SOLID 不得因路线简化、既有代码问题或测试通过而豁免。

### 7.5 完成证据

- 实际审核目标：至少包括 `CodeBaseSHA`、`HeadSHA` 和 `CodeBaseSHA..HeadSHA`；
- 修改摘要与文件；
- 构建和测试命令、环境与结果；
- 自主探索的重要发现；
- 未运行项和证明缺口；
- 独立 Review 结论；
- 是否影响上游文档、Context L1 或其他任务。

编码任务未创建任务分支交付 commit 时，不得进入 `InReview`。纯调查、纯文档或项目负责人批准的特殊任务可以不创建代码 commit，但必须在任务契约中事先声明候选形式和理由。

### 7.6 工期与关键路径

估算不得只计算编码时间。至少分别列出：

- 实现与自检；
- Coding Review；
- 一轮预期返工；
- 迭代合并；
- 集成验证与系统 Review；
- 证据整理、人工门禁和外部等待。

同时给出理想、正常和包含一轮返工的保守工时，并标明可并行部分与串行关键路径。

## 8. 任务状态与统一状态交换面

### 8.1 唯一状态真源

项目必须同时指定 Git 管理的详细开发任务文档和 Hermes 台账（`LedgerLocation`）。详细开发任务文档保存任务定义和最近一次持久快照；Hermes 台账（本地 JSON 状态文件 + 可选 SQLite，不进 Git）是活动迭代中任务运行状态的唯一实时真源，由 Hermes 单实例维护。

`TaskDocumentBaselineRef` 继续标识不可变任务定义。状态交换区的例行变化不改变已派发任务的需求、设计或代码审核基线；任何发生在状态交换区之外的内容变化仍按文档变更流程判断是否使 Context、Review 或派发失效。

Hermes 不得再把跨任务 API、UI 状态或聊天上下文作为任务状态发现入口。台账缺失时，从详细开发任务文档的持久快照和 Git 恢复；不得用旧快照覆盖台账中的更高 `StateRevision`。

### 8.2 台账最小结构

`LedgerLocation` 由 Hermes 维护，保持可机读；详细开发任务文档中的 `TASK-STATE-EXCHANGE` 块仅作为最近一次持久快照，不是运行期写入目标。

迭代级至少包含：

```text
SchemaVersion, IterationID, CanonicalTaskDocumentPath, LedgerLocation,
StateRevision, UpdatedAt, ConsumedRevision
```

每个开发、Review、返工、集成、验证或求助阶段使用独立 `RecordID`，至少包含：

```text
RecordID, TaskID, TaskType, Stage, InvocationID, ProducerRole,
ExecutionRef, TaskState, SignalState, SignalRevision,
ExecutionStatus, HeadSHA, ReviewTarget, Verdict, IntegrationCommit,
ProducedAt, ConsumedAt, ConsumedBy, NextAction, Summary
```

`SignalState` 只使用：`None`、`PendingConsumption`、`Consumed`、`Superseded`。执行 Agent 通过载体通道回报结构化结果，由 Hermes 消费后递增 `SignalRevision` 与 `StateRevision`，写入 `PendingConsumption`；Hermes 完成验证和后续动作后才改为 `Consumed`。同一 `RecordID + SignalRevision` 是幂等消费键。

### 8.3 写入与幂等规则

- 执行 Agent **不直接写台账**；通过其载体通道输出结构化协议头，由 Hermes 消费后幂等写入台账（事件 + cron 兜底）；
- 子任务开始、求助、完成、Review 结论、返工提交和集成结果必须先输出结构化协议头，再输出 final；final 是详细证据，不是状态发现入口；
- 子任务只能回报自己的状态记录，不得更新其他任务的汇总状态、批准自身实现或派发后续任务；
- Hermes 是汇总状态和消费确认的唯一写入者；发现 `PendingConsumption` 后，才按记录中的精确 `ExecutionRef` 定向读取对应执行载体；
- 台账写入幂等由 `DispatchKey = IterationID + TaskID + Stage + TargetIdentity` 与 `RecordID + SignalRevision` 去重保证（单实例无锁）；
- 状态写入失败时不得声称状态已发布；Hermes 的下一轮对账只依据台账，不扫描全部执行载体兜底；
- 台账不得保存长日志、完整 diff 或大段 final，只保存定位和验证所需的摘要、SHA、Verdict、执行引用与下一动作。

### 8.4 稳定任务状态

任务汇总状态使用：

| 状态 | 含义 |
|---|---|
| Planned | 已规划，尚不可或尚未开始 |
| Ready | 依赖、分支、基线和派发清单已满足，可以启动 |
| InProgress | 正在开发或返工 |
| Submitted | 任务分支已产生交付提交，等待独立 Review |
| InReview | 已提交独立 Review |
| ChangesRequested | Reviewer 已提出需关闭的 Findings，等待授权返工 |
| TaskAccepted | Level 0 已通过 |
| MergePending | 已通过 Level 0，等待独立迭代集成任务 |
| Integrated | 精确已审核提交已合入当前迭代分支且推送成功 |
| IntegrationVerified | 合入后受影响集成检查已通过 |
| Blocked | 有明确阻塞 |
| Cancelled | 已批准取消 |

临时心跳和工具调用细节无需逐轮写入 Git 文档；但 `InvocationID`、`ExecutionRef`、当前 `TaskState`、待消费信号、目标 SHA/Verdict、生产与消费时间必须由 Hermes 幂等写入台账。

`TaskAccepted`、`Integrated` 和 `IntegrationVerified` 不能互相替代。`ComponentVerified`、`SystemVerified`、`ExternalVerified` 和 `MergeApproved` 属于候选版本，不属于单任务状态。

## 9. 调度与返工

- 一个任务同一阶段只能有一个有效开发实例，除非已拆成互不冲突的子任务；
- 每次派发必须具有唯一 `InvocationID`、幂等 `DispatchKey` 和不可变代码/文档基线；
- 开发提交后进入独立 Review；
- `ChangesRequested` 返回原任务和原开发者或批准的替代者；
- 已授权返工继续使用同一任务 ID 和原任务分支，产生新的 `HeadSHA` 并使原 Review 结论失效；
- 只有 Review 通过且证据有效，总调度才更新 `TaskAccepted`；
- `TaskAccepted` 后由独立迭代集成任务合并准确 `HeadSHA`，不得由开发者自行合并；
- 调度派发后由 Hermes 通过事件（飞书 / Codex 网关轮询）+ cron 兜底消费台账；发现 `PendingConsumption` 才定向读取该记录的 `ExecutionRef` 并立即处理；
- cron 对账只读取 Hermes 台账和必要 Git 事实，不遍历任务列表、不逐载体读取、不依赖跨任务 API 事件；
- 任务创建、文档状态生产/消费、暂停、恢复和 Canary 按 `09-Hermes调度与运行时台账规范` 执行；台账不可用时按恢复协议处理，不得继续派发；
- 项目明确指定的执行机制不得被其他机制未经授权替代（禁止伪独立自审）；
- 巡检不得把一次编译/测试失败或未完成代码当作最终阻塞。只有执行者明确报告阻塞、发现授权/范围冲突，或经连续检查确认无活动且无法恢复时才可中断；
- 同一 Finding 连续两轮未关闭时，总调度必须执行根因分类；同类问题第三次出现时停止机械循环，升级为实现能力、设计歧义、证据缺陷或候选绑定问题处理；
- 角色提示词和允许状态以 `07` 为准。

## 10. Context L1 与 Context L2

- Context L2 是否需要，完全按 `06` 的风险触发规则执行；
- 轻量任务和单一执行者的局部任务通常使用任务简报，不建立独立 Context L2；
- **Context L2 生成触发（与 `09` §3.2 一致）**：当 `ContextL2Policy=Required` 时，Hermes 在派发 Implementer 前先进入任务状态 `ContextGenerationPending`，派发 Doc/Design Reviewer 生成 Context L2（须在其依赖满足后），其完成信号写回台账后才推进到 `Ready` 并派发 Implementer；`ContextGenerationPending` 缺完成信号时的停滞检测与升级见 `09` §11.1；
- Context L1 只有在稳定架构、全局约定、核心模型或权威入口实质变化时才更新；
- 迭代收尾检查 Context L1 是否受影响；无变化只记录清单结论，不建立独立 `NoChange` 开发任务或 Review；
- 有变化时必须建立正式文档任务并独立审核其准确性；该任务要么作为迭代收尾阻塞项完成，要么由项目负责人明确批准为带 ID、责任人和完成时间的后续任务，不得只记录 `Changed` 后静默关闭迭代。

## 13. 审核清单

- [ ] 开发路线与实际风险相称；
- [ ] 任务目标、依赖和授权边界明确；
- [ ] Coding、返工、迭代合并、集成验证和主分支合并任务已经区分；
- [ ] 编码任务具有唯一任务分支、worktree、CodeBaseSHA、ReviewedCommitRange/ReviewedCommitSet 和 MergeTarget；
- [ ] 代码、需求、设计、任务和 Context 基线均不可歧义，未引用其他可变工作区作为唯一真源；
- [ ] 高风险调度已配置 IterationID、CanonicalTaskDocumentPath、LedgerLocation 台账 Schema、协议版本、恢复策略和 Canary；
- [ ] 每次派发在运行时绑定 InvocationID、执行机制和幂等 DispatchKey；
- [ ] 依赖类型和所需状态明确，没有复用同一任务 ID 表示前后两次验证；
- [ ] 持续集成点和正式 Level 1 均已安排；
- [ ] 关键跨任务路径有集成责任，或明确 `N/A`；
- [ ] Context L2 按风险触发，没有为低价值任务强制生成；
- [ ] Context L1 只在稳定事实变化时更新；
- [ ] SOLID 保持硬门禁，证据深度与风险相称；
- [ ] 角色、验证、Review 和合并规则引用唯一真源；
- [ ] 已配置唯一 `CanonicalTaskDocumentPath`、Hermes 台账（LedgerLocation）、版本号与幂等写入；
- [ ] Hermes 台账可用，缺失时按恢复协议处理；指定执行机制不会被其他机制未经授权替代；
- [ ] 外部副作用和无副作用验证路径明确；
- [ ] 工期包含 Review、返工、集成、证据与人工门禁；
- [ ] 待审核事项清零。

## 14. 完成定义

只有在路线选择合理、任务边界和依赖可执行、系统交界有责任人、Context 策略与风险相称、SOLID 和验证责任明确，且适用的开发任务文档状态面、不可变基线、恢复策略与 Canary 已就绪，并由项目负责人完成必要审核后，开发任务才能启动。
