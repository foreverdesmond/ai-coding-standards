# 文档审核与变更控制规范

> 规范版本：V2.4
> 规范状态：待审核（V2.3 仍为上一已审核基线）
> 适用对象：背景分析、需求规格、详细设计、详细开发任务及其后续修订
> 定稿日期：2026-08-11
> 修订日期：2026-08-15

## 1. 目的

本规范确保项目在多轮人机讨论中逐渐完善，而不会因为聊天上下文、口头确认或下游实现变化而失去正式基线。

文档审核的目标不是一次写完，而是让每个重要决定经历：

```text
提出 → 记录 → 分析影响 → 待审核 → 用户确认 → 写入基线 → 向下游传播
```

## 2. 审核权与职责

### 2.1 项目负责人

- 对业务范围、用户行为、风险接受、架构冲突和最终文档拥有批准权；
- 可以批准、否决或要求继续比较方案；
- 只有项目负责人能宣布文档整体审核通过；
- 可以授权特定独立执行任务执行代码、数据库、外部系统和 Git 操作，但各种授权互不自动包含；数据库或持久状态授权不得转给 CodingTask、ReworkTask、Reviewer 或普通合并任务。

### 2.2 Codex

- 负责调查、提出问题、比较方案、编辑文档和维护状态；
- 对明显错误应提供证据和理由，不机械迎合；
- 不得替项目负责人批准重要取舍；
- 不得把用户的探索性表达自动视为最终决定；
- 用户确认后必须把结论写入正式文档，而不是只在聊天中回复“明白”。

### 2.3 开发与审查人员

- 以最新“已审核通过”版本为基线；
- 发现实现与基线冲突时停止相关部分并提交变更请求；
- 不得通过代码事实反向静默修改需求或设计。

## 3. 审核方式

### 3.1 逐项审核

每份文档应在末尾提供待审核清单。推荐格式：

```markdown
- [ ] DEC-001：一条业务记录对应一个搜索文档。
- [ ] DEC-002：列表使用派生摘要，详情以数据库为真源。
```

用户确认后更新为：

```markdown
- [x] DEC-001：已通过，确认时间 2026-08-11。
```

确认时应同时更新正文，不能只勾选清单而正文仍保留旧方案。

### 3.2 分章节审核

复杂文档可以按以下方式进行：

1. Codex先提交完整草稿或一个逻辑完整章节；
2. 列出本轮需要决定的事项；
3. 用户逐项给出意见；
4. Codex修改正文、决定记录和待审核清单；
5. Codex说明剩余未审核章节；
6. 所有章节完成后，再请求整体审核。

### 3.3 整体审核

标记“已审核通过”前必须确认：

- 待审核复选框为零；
- 未决问题没有被隐藏在正文；
- 上游基线版本正确；
- 正文、示例、图、验收清单和决定记录一致；
- 范围和非范围明确；
- 文档版本与更新时间已更新；
- 项目负责人明确表示整体通过。

## 4. 决定记录

以下决定必须保留记录：

- 改变数据粒度、身份或真源；
- 改变用户可见行为或业务口径；
- 改变范围、兼容性或一致性；
- 选择或拒绝重要架构方案；
- 接受明显性能、成本、安全或运维取舍；
- SOLID 与既有架构发生冲突；
- 取消或推迟原本在本期的能力。

标准格式：

```markdown
### DEC-001：<决定标题>

- 状态：待审核 / 已通过 / 已取代
- 背景：
- 选项：
- 决定：
- 理由：
- 影响范围：
- 确认人：
- 确认时间：
- 取代关系：无 / DEC-000
```

删除旧决定会丢失设计历史，因此被推翻时应标记“已取代”并链接新决定。

## 5. 版本规则

推荐使用 `V主版本.次版本`：

- 草稿小幅补充：增加次版本，如 `V0.2 → V0.3`；
- 首次整体审核通过：进入 `V1.0`；
- 审核后新增但兼容的规则或设计：`V1.1`；
- 改变核心范围、业务语义、数据身份或不兼容设计：`V2.0`；
- 纯错别字和不改变语义的排版修正可不升级，但应更新时间。

文档顶部必须记录当前版本，上游文档引用必须带版本，避免只引用文件名。

## 6. 上游变更传播

### 6.1 影响关系

```text
背景变化
  → 可能影响需求、设计、任务

需求变化
  → 必须检查设计、任务和已有代码

设计变化
  → 必须检查任务、上下文包、提示词、测试和已有代码

任务编排变化
  → 通常不反向改变需求和设计，但可能暴露设计遗漏

验证或现实运行发现缺陷
  → 必须判断实现、测试、设计、需求、上下文或规范是否存在缺口
```

### 6.2 处理步骤

1. 在上游文档记录变更请求和新决定。
2. 判断是否需要重新审核该文档。
3. 把所有受影响的下游文档标记为“待同步”。
4. 建立影响清单：章节、任务、代码、脚本、测试和人工步骤。
5. 更新下游正文、追溯矩阵和版本。
6. 对实质变化重新逐项审核。
7. 下游重新通过后才能继续相关开发。
8. 使受影响的上下文包、Review 结论、测试证据和合并批准失效，直至重新校验。

不得只修改详细开发任务来绕过需求或设计变更。

## 7. 开发期间的变更请求

开发中遇到以下情况应暂停相关任务：

- 需求规则无法确定；
- 详细设计与现有代码或平台行为明显冲突；
- 需要修改禁止范围；
- 性能估算与实测差异足以改变方案；
- 外部平台版本或限制与设计不符；
- 为通过测试必须改变用户可见行为；
- 发现安全或数据丢失风险。
- 上下文包与当前代码、生产入口或依赖图不一致；
- 现实运行发现自动化测试未覆盖的系统行为；
- 未经授权的代码变化，或变化改变需求、设计、范围或风险接受；已授权的 Review 返工不属于此项，按原任务分支返工闭环处理。

变更请求格式：

```markdown
### CR-001：<标题>

- 发现阶段：
- 发现人：
- 当前基线：
- 事实与证据：
- 受影响需求/设计/任务：
- 可选方案：
- 推荐与理由：
- 当前任务状态：Blocked
- 项目负责人决定：待审核
```

只影响内部实现且不改变已审核行为、边界和风险的细节，可由调度/审查者在设计约束内处理，并记录在任务证据中。

## 8. 状态一致性

### 8.1 文档状态

文档首页状态、末尾审核清单和 README 索引必须一致。

### 8.2 任务状态

详细任务章节、主状态表和同一文档中的结构化任务状态交换区必须一致。不得出现任务正文 `TaskAccepted`、总表仍为 `InProgress` 的情况。

项目必须同时指定唯一 `CanonicalTaskDocumentPath` 和 `SharedRuntimeStatePath`。前者保存 Git 管理的任务定义与最近一次持久快照；后者是不进入 Git、所有 worktree 共同可写的 JSON，也是任务状态发现、子任务状态生产和 Coordinator 消费确认的唯一实时真源。聊天上下文、UI 状态、跨任务读取 API、文档快照和派生台账不得覆盖共享 JSON 中更高的 `StateRevision`。

状态交换区的例行更新不改变 `TaskDocumentBaselineRef` 所标识的不可变任务定义，也不自动使代码候选、测试或 Review 失效。发生在状态交换区之外的任务定义变化仍必须按本规范审核。

共享状态缺失、损坏、版本回退或无法解释任务与 Git 差异时，Coordinator 必须进入 `RecoveryOnly`。恢复优先依据开发任务文档中的最后有效快照和 Git；只有恢复出的记录明确标记 `PendingConsumption` 或证据缺失时，才定向读取对应 `ExecutionThreadID`，不得恢复为全量跨线程扫描。

### 8.3 代码状态

- 文档已通过不代表代码已完成；
- 代码已提交不代表任务已验收；
- 全部任务已验收不代表真实环境已验证；
- 真实环境已验证不代表已经授权发布；
- 已推送功能分支不代表已经合并到项目默认主分支。
- `TaskAccepted` 不代表已合入迭代开发分支；
- `Integrated` 不代表已通过合并后集成验证；
- `IntegrationVerified` 不代表迭代候选已经 `ComponentVerified`；
- `TaskAccepted` 不代表 `ComponentVerified`；
- `ComponentVerified` 不代表 `SystemVerified`；
- `SystemVerified` 不代表 `ExternalVerified`；
- Review 通过只对记录的精确提交有效。

这些状态必须分别陈述。

## 9. 证据要求

### 9.1 文档证据

- 代码路径和必要行号；
- 数据查询时间、环境和口径；
- 日志文件与关键 run 标识；
- 官方资料链接和核验日期；
- 用户明确确认的决定。

### 9.2 开发证据

- 实际修改文件；
- 构建和测试命令及结果；
- 未运行测试及原因；
- 静态依赖或架构检查；
- 关键失败场景测试；
- 审查者结论。
- 基线提交、提交候选和审查提交；
- 测试替身及其不能证明的内容；
- `NotRun` 阻塞阶段、责任人和例外批准记录。

真实编码任务的最小身份字段为 `TaskBranch`、`CodeBaseSHA`、`HeadSHA` 和 `CodeBaseSHA..HeadSHA`。worktree 路径、文件修改时间、聊天摘要和 UI 状态只能作为导航或辅助证据，不能替代 commit/tree/diff 内容身份。V2.3 制品中的 `BaseSHA` 是 `CodeBaseSHA` 的兼容旧名；V2.4 新制品只使用 `CodeBaseSHA`。

当已审核需求、设计或任务文档不在代码 `CodeBaseSHA` 中时，必须分别登记不可变的 `RequirementsBaselineRef`、`DesignBaselineRef` 和 `TaskDocumentBaselineRef`。不得用持续变化的主工作区路径代替文档内容身份。

不得伪报真实数据库、搜索引擎或其他外部环境测试。没有环境时应写“未执行，待项目负责人手工验证”。

### 9.3 证据有效范围

- 测试和 Review 必须绑定仓库、不可歧义审核目标、环境和时间；
- 同一审核目标的相同快速测试可以复用结果，Reviewer 仍应按风险抽查或复跑；
- 审核目标变化后，受影响证据自动失效；纯文档变化是否使代码测试失效由 Reviewer 记录判断；
- 开发者测试证明可复现性，Reviewer 测试证明独立性，两者不应通过机械重复代替反例设计；
- 日志、截图和 Agent 总结必须能追溯到原始命令或运行记录。
- 证据中的哈希算法必须准确命名；SHA-1、SHA-256、Git commit ID 和 Git tree ID 不得混称；
- 证据文档不得把自身哈希作为自身有效性的前置条件，也不得形成“更新证据导致候选失效”的自引用循环；
- 验证命令必须可直接复制执行，或引用受版本控制且已冻结版本的脚本；被排版换行破坏的命令不构成可复现证据；
- 文件修改时间只能辅助判断时序，不能证明文件内容相同；
- 纯文档、台账或证据变化且代码 `HeadSHA` 未变化时，不自动使已有代码测试和 Coding Review 失效；Reviewer 只需判断该文档变化是否改变了审核基线。
- 真实编码任务必须登记 `ReviewedCommitRange`、`ReviewedCommitSet` 和 `IntegrationMethod`；实际集成的提交集合必须与已审核集合一致。
- 从丢失台账恢复的证据必须标记 `Recovered`、来源、原始时间、恢复时间、指纹和置信度；不得伪装成实时收到的原始事件。
- 不同来源只证明其职责范围：Git 证明提交和包含关系，Reviewer final 证明 Verdict，任务系统证明执行历史，用户消息或正式记录证明授权。不得用任一来源越权推断其他事实。
- 用户提供的完整子任务结果应先登记并核验；无法读取原任务时进入 `PendingVerification`，不得被 UI 标签覆盖，也不得未经核验直接推进门禁。

## 10. 合并候选冻结与批准有效性

### 10.1 候选冻结

进入 Coding Review、Level 1 整体 Review、Level 3 最终验收或最终合并审核前，必须记录不可歧义候选目标。真实编码任务默认使用 Git commit 与 `CodeBaseSHA..HeadSHA`；迭代和版本候选默认使用 commit/tree。纯文档、调查或经项目负责人事先批准的特殊任务才可使用 PR revision、diff hash 或稳定工作区快照。冻结不是禁止修复，而是规定：目标实质变化会产生新的候选，并使受影响结论失效。

活动任务台账、临时巡检时间、Agent 状态和证据文档自身不得进入代码候选哈希。候选证据可以引用候选 SHA，但不能通过修改自身来改变被引用候选的身份。

开发任务文档状态交换区保存实时状态；长日志、备份和租约可以位于项目配置的非候选目录。若提供状态校验工具，文档锁、版本复查、状态转换和事件去重必须通过工具完成。具体字段、恢复和 Canary 以 `09` 为准。

### 10.2 分支角色

项目必须配置实际分支策略并保留等价状态与证据门禁。`08` 提供推荐默认映射，但不限制 trunk-based、发布分支或功能开关等其他策略。

### 10.3 最终批准

最终合并审核者只能对冻结候选给出 `MergeApproved` 或 `MergeBlocked`，不得执行合并。项目负责人的合并授权必须晚于有效审核结论；合并目标、来源和候选必须精确匹配。只有独立 `MainMergeTask` 可以执行主分支合并，且不得夹带开发修改。合并后仍需单独决定是否发布。

迭代分支同样遵守职责分离：Coding Reviewer 给出 `TaskAccepted` 后，只能由独立 `IterationMergeTask` 按 `ReviewedCommitSet` 和 `IntegrationMethod` 合入。合并冲突若需要改变实现，必须退回原任务或建立修复任务并重新 Review；approved squash 必须提供等价 diff 证据。

## 11. 现实缺陷反馈闭环

以下情况必须执行文档与流程回查：已批准需求/设计与现实冲突、同类缺陷重复发生、测试或 Review 出现系统性漏检、环境差异导致高影响问题，或涉及安全、数据、兼容和事故。普通局部 Bug 可以在任务证据中说明无需扩大回查。

需要回查时判断：

| 问题类型 | 必须回查 |
|---|---|
| 需求遗漏 | 背景、需求、验收层级 |
| 设计遗漏 | 生命周期、资源、异常、测试策略 |
| 任务遗漏 | 拆分、交界责任、授权范围 |
| 上下文遗漏 | 已知事实、未知项、自主探索范围 |
| Review 漏检 | 角色提示词、反例和证据门禁 |
| 环境差异 | Level 1–3 定义和 NotRun 决策 |
| 通用流程缺陷 | 本目录规范及提示词模板 |
| 调度状态丢失、重复派发或事件漏读 | `09`、Coordinator/巡检模板及调度 Canary |

通用规范只吸收可跨任务复用的规则，不写死单次事故细节。

## 12. 冲突处理

当以下内容冲突时，Codex不得擅自选择：

- 用户新意见与已审核决定；
- SOLID 约束与既有代码结构；
- 性能目标与平台免费额度；
- 数据正确性与简化实现；
- 本期范围与为了实现所需的额外重构；
- 自动化测试要求与缺少真实环境。

Codex应提供：事实、冲突点、至少两个可行选项、各自影响和推荐理由，并由项目负责人裁决。

## 13. 文档归档

- 新版本完全取代旧文档时，旧文档标记“已取代”，保留链接和原因。
- 临时调查记录可以归档，但其已确认结论必须进入正式文档。
- 不应删除已影响实现的历史决定。
- README 应指出当前有效版本和推荐阅读顺序。

## 14. 审核总门禁

- [ ] 各制品已通过其本地审核清单，不在本文件重复逐项检查；
- [ ] 所有待审核项清零，上下游版本一致；
- [ ] Context L2、Review 和测试证据与当前审核目标匹配；
- [ ] 已批准、已编码、已验收、已人工测试、已合并和已发布未被混为一谈；
- [ ] 冻结候选与 Review、测试和合并批准一致；
- [ ] 代码基线和适用的需求、设计、任务文档基线均不可歧义；
- [ ] 开发任务文档状态交换区唯一、可解析且版本单调；派生审计缓存不进入候选哈希；
- [ ] 恢复证据、用户导入证据和原始事件的来源及置信度没有混用；
- [ ] 达到触发条件的现实缺陷已经完成文档与流程回查。

## 15. 完成定义

只有当正式文档已保存全部关键决定、状态和证据，上下游基线一致，并且项目负责人明确批准时，审核才真正完成。聊天中的口头共识如果没有写回文档，不视为可复用的项目规范。
