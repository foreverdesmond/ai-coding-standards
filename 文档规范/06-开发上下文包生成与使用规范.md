# 开发上下文包生成与使用规范

> 规范版本：V2.5
> 文档状态：已审核通过（V2.5 定稿基线）
> 适用范围：按风险需要独立 Context L2 的开发任务
> 作者：WorkBuddy（受 Hermes 总调度委派）
> 创建日期：2026-08-11（V2.3 定稿）
> 最后更新：2026-08-20
> 审核人：Richy（已审核）

## 1. 定位

上下文包用于大型、长周期、多 Agent 或高风险任务，减少重复读取并控制任务边界。它是导航材料，不是项目事实全集、需求真源、设计替代品或免除代码调查的证明。

```text
Context L1：项目已有的稳定架构资料
  → Context L2：按风险生成的单任务导航包
  → Context L3：执行者对当前代码和运行事实的自主调查
```

Context L3 是调查过程和代码基线，不是另一份必须维护的文档。

## 2. Context L2 触发条件

出现以下一项或多项时，通常应生成独立 Context L2：

- 多 Agent 分工或任务跨越多个模块；
- 长周期任务可能经历上下文压缩、暂停、重启或执行实例替换；
- 需求、设计决定、授权范围或兼容约束较多；
- 生产入口、并发、资源生命周期、持久化、安全或外部协议风险较高；
- 并行任务需要精确文件所有权；
- Reviewer 需要明确识别替身证明边界和未知项。

以下情形通常不需要独立 Context L2：

- 单一执行者完成的局部、低风险、短周期任务；
- 任务简报已经完整表达目标、范围、风险和验证；
- 上下文包只是机械复制需求、设计和任务正文。

不生成 Context L2 时，任务简报仍必须包含必要基线、授权边界和停止条件。是否触发由开发路线和风险共同决定，不以节省 Token 作为唯一理由。

## 3. Context L1

- **Context L1 的标准入口（物理载体）是仓库根目录的 `AGENTS.md`**，为所有执行 Agent 提供位置可预测、跨任务稳定的项目级操作说明（技术栈、构建/测试命令、编码规范、分支策略、工具权限）；
- `AGENTS.md` 支持分层与就近覆盖（closest-wins）：`global`（用户级）→ 项目根 → 子包级，离被编辑文件最近的一份优先；冲突优先级为「用户当前显式指令 > 就近 `AGENTS.md` > 远程文档」；
- 除 `AGENTS.md` 外，Context L1 还可复用 ADR、架构文档、编码规范或其他权威资料；通用规范不强制目录和文件名称；
- 只保存跨任务稳定、会影响未来判断的事实和规则；
- 详细历史、临时调试、任务状态和完整代码清单不进入 Context L1；
- 缺少正式 `AGENTS.md` 时，可以直接引用权威代码和文档，不强制先建立一套新目录。

## 4. 最小内容与风险附加项

### 4.1 所有 Context L2 的最小内容

1. 任务目标、风险和系统集成责任；
2. 仓库、任务分支、worktree、`CodeBaseSHA` 和不可歧义代码基线；
3. 需求、设计、任务和 Context L1 引用；
4. 已验证事实及证据；
5. 未验证假设、未知项和证明缺口；
6. 允许修改的职责或文件边界；
7. 必须自主探索的只读范围；
8. 禁止行为和外部操作；
9. 验证、Review、失效和停止规则。

### 4.2 按风险增加

- 关键生产入口、调用者、间接依赖和配置路径；
- 生命周期、并发和资源所有权；
- 详细正常、失败、取消和恢复路径；
- 测试替身的“能证明/不能证明”矩阵；
- 精确文件所有权；
- Level 0–3 的证据分工；
- 暂停、重启和执行实例切换的恢复点。

不得为了满足模板而填写与任务无关的空章节。

## 5. 事实、假设与未知项

- 已验证事实必须附代码、配置、日志、测试或已审核决定等来源；
- 假设必须可证伪，并说明验证阶段；
- 未知环境、数据、凭据和外部行为必须映射到 `NotRun`、人工验证或变更请求；
- 不得把“设计计划如此”写成“当前已经如此”。

## 6. 自主探索

Context L2 只能提供起点。开发者必须按风险自主检查：

- 当前工作区和审核基线；
- 当前任务分支、worktree 与 `CodeBaseSHA` 是否和任务契约一致；
- 目标接口、实现、消费者和相关测试；
- 生产启动、注册或实际创建入口；
- 工厂、Service Locator、反射、插件、`Lazy<T>` 和静态状态等间接依赖；
- 生命周期、并发单元和资源所有权；
- Mock/Fake/内存替身及其证明缺口。

低风险任务可以用简洁探索摘要；高风险任务应沿至少一条成功路径和一条失败路径追踪到系统边界。

发现普通局部差异时可以在批准职责范围内纠正并报告。只有差异影响用户行为、已批准设计、风险接受或修改权限时才进入 `Blocked`。

## 7. 修改与只读范围

- 默认按职责或模块授权修改，并允许直接相关测试与局部接线；
- 并行冲突、敏感文件和高风险资源才使用精确文件清单；
- 只读调查可以合理扩展，但不能借此扩大修改授权；
- 超出职责边界的修改必须先更新任务授权。

## 8. 测试替身声明

存在实质证明缺口时使用：

| 被替换依赖 | 替身 | 保留的真实路径 | 能证明 | 不能证明 | 后续 Level |
|---|---|---|---|---|---|

替换生产注册入口、生命周期、数据库 Provider、外部协议或并发资源后，不得用该测试证明对应真实行为。

## 9. Reviewer 的独立视角

- Reviewer 应先依据需求、实际审核目标、diff 和代码形成独立风险模型；
- 然后读取 Context L2，核对开发者是否遗漏事实、未知项或证明缺口；
- Context L2 不限制 Reviewer 的只读调查范围；
- Reviewer 不应只沿用包内推荐文件和风险清单。

## 10. 失效条件

以下变化影响任务时，Context L2 进入 `Stale`：

- 需求、设计、任务授权或 Context L1 实质变化；
- 相关入口、接口、配置或代码基线变化；
- 任务分支、`CodeBaseSHA`、依赖状态或合并目标变化；
- 包内事实被证伪；
- 风险、系统集成责任或修改边界变化；
- 返工实质改变原任务方案。

重新校验只需更新受影响部分和版本，不必机械重写整包。

## 11. Context L1 对账

- 只有稳定架构、全局约定、核心模型、权威入口或长期禁止项发生实质变化时才更新 Context L1；
- 迭代收尾只需判断 `Changed / NoChange`；
- `NoChange` 记录在收尾清单，不创建独立开发任务和 Review；
- `Changed` 时建立文档修改并独立核对准确性；
- `Changed` 必须在迭代关闭前完成，或由项目负责人批准为带 ID、责任人和完成时间的后续项；不得停留在无责任人的结论；
- 不得把未经批准的代码偏差反向写入 Context L1。

## 12. 模板

```markdown
# <TASK-ID> Context L2

> Status: Draft / Ready / Stale / Archived
> Risk:
> TaskBranch:
> WorktreePath:
> CodeBaseSHA:
> RequirementsAndDesign:
> ContextL1:
> GeneratedBy:
> ValidatedAt:

## 1. 目标、风险与系统集成责任
## 2. 已验证事实及证据
## 3. 未验证假设、未知项与证明缺口
## 4. 允许修改与必须自主探索
## 5. 禁止行为与外部操作
## 6. 关键运行路径和风险附加项
## 7. 测试、Review、失效与停止规则
```

## 13. 审核清单

- [ ] 任务确实满足 Context L2 触发条件；
- [ ] 没有机械复制上游文档；
- [ ] 事实、假设和未知项分开；
- [ ] 任务分支、worktree、CodeBaseSHA 和依赖状态与当前任务契约一致；
- [ ] 修改范围不会抑制必要的自主调查和直接相关修复；
- [ ] 替身证明缺口和系统风险按需记录；
- [ ] Reviewer 可以先形成独立视角；
- [ ] 失效规则可执行。

## 14. 完成定义

当触发条件成立时，只有 Context L2 绑定有效基线、暴露未知项、提供足够探索路线且未替代自主调查，任务才可使用它进行派发。未触发时，合格任务简报即可。
