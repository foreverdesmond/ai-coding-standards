# 开发验证、代码审查与合并门禁规范

> 规范版本：V2.3  
> 规范状态：待审核  
> 适用范围：所有需要代码 Review、集成验证、分支合并或真实环境验收的开发任务  
> 修订日期：2026-08-15

## 1. 目的

本规范区分局部正确、组件集成、生产形态系统运行和真实外部环境，规定每一层的执行者、证据、分支动作和返工闭环。

## 2. 状态门禁与默认分支策略

Level 0–3 是通用验证状态，不依赖某一种 Git 分支模型。下表是推荐默认映射：

| 逻辑角色 | 作用 |
|---|---|
| 任务分支 | 单任务实现、返工和开发 commit |
| 迭代开发分支 | 由独立集成任务汇总 Level 0 已通过的精确提交 |
| 长期集成分支 | Level 1 通过后进行真实系统验证 |
| 稳定分支 | Level 3 和最终审核通过的稳定候选 |

项目可以使用 trunk-based、短分支、发布分支、功能开关或其他策略，也可以合并部分物理分支，但必须保留等价的候选隔离、证据、回退和授权门禁。真实编码任务默认使用独立任务分支；偏离默认策略必须由项目负责人事先批准。实际分支策略由开发任务配置。

### 2.1 Git 权限边界

- 开发和返工只允许在本任务分支创建 commit；
- Coding Reviewer、系统 Reviewer 和最终合并 Reviewer 只读；
- 只有独立迭代集成任务可以合并 `TaskAccepted` 的精确提交到迭代开发分支；
- 只有独立主分支合并任务可以在 `MergeApproved` 和明确授权后合并精确候选到主分支；
- Reviewer 不得兼任同一候选的合并执行者；任何进入共享迭代、长期集成或主分支的动作都由独立合并任务执行。

## 3. Level 0：单任务验证

### 3.1 目标

证明一个任务在批准范围内局部正确、可构建、可测试并符合设计。

### 3.2 执行

- 开发者运行定向编译、单元测试和受影响组件测试；
- 开发者在唯一任务分支提交代码，并记录 `BaseSHA`、`HeadSHA` 和 `BaseSHA..HeadSHA`；
- 独立 Coding Reviewer 检查实际审核目标，复跑最小必要测试并形成独立风险假设；存在重要可执行风险时验证反例，否则记录无需额外反例的依据；
- 返工后原 Review 结论失效，重新复核。

### 3.3 通过条件

- 需求、设计、SOLID、范围、错误和安全门禁通过；
- 所有阻塞任务验收的测试通过；
- 开发提交与 Reviewer 审核的是同一不可歧义目标；
- 状态更新为 `TaskAccepted`。

### 3.4 分支动作

`TaskAccepted` 只授予进入独立迭代集成任务的资格，不自动表示代码已经合入。集成执行者必须合并 Reviewer 实际审核的精确 `HeadSHA`；成功后记录 `Integrated`。合并后受影响的持续集成检查通过，才记录 `IntegrationVerified`。不得据此宣称版本已经通过 Level 1–3。

## 4. Level 1：迭代组件集成

### 4.1 目标

证明全部计划任务组合后，自动化组件行为和跨任务接线符合批准基线。

### 4.2 前置条件

- 每个任务进入候选后已经执行受影响的持续集成检查；
- 全部纳入候选的计划任务为 `Integrated`，且受影响检查达到 `IntegrationVerified`；
- 迭代候选提交冻结；
- 无无法解释的工作区变化；
- 系统集成责任任务已完成。

### 4.3 覆盖

- 解决方案构建和全量自动化；
- 组件、契约、Fake/Mock/内存集成；
- 生产组合根中可安全自动化的注册和关键入口激活；
- 跨任务接口、配置、状态和兼容；
- 系统集成 Reviewer 的独立风险假设及按需反例；
- 测试替身证明边界与 Level 2/3 `NotRun` 清单。

### 4.4 通过条件与分支动作

系统集成 Reviewer 给出 `ComponentVerified`，项目配置中阻塞 Level 1 的 `NotRun` 为零后，执行项目分支策略；默认允许进入长期集成分支。

Level 1 不是生产外部环境通过证明。它允许后续真实测试发现问题并返工。

## 5. Level 2：生产形态系统验证

### 5.1 目标

在项目指定的集成候选上验证生产形态入口、配置、Scope、并发、持久化调用链和关键系统行为。

### 5.2 执行方式

项目可以选择人工、半自动或自动。默认推荐：Agent 准备配置和步骤，项目负责人授权并执行，Agent 分析日志和证据。

Level 2 可以使用现有集成环境和可恢复业务数据。是否允许写入由项目负责人根据项目数据性质批准。

### 5.3 数据库与持久资源安全

- 任何可能修改数据库、索引、存储或真实外部状态的验证，不得由开发、返工、Coding Review、系统 Review 或合并执行任务完成；必须使用独立验证任务，并由项目负责人明确授权执行主体；
- 默认禁止 Agent 自动创建、删除、清空、重建数据库、Schema、持久卷、索引或外部资源；
- 禁止把临时数据库或容器作为所有项目的强制条件；
- 任何破坏性操作都需要精确目标、影响说明和单次明确授权；
- 未获授权时记录 `NotRun` 或采用非破坏性人工验证；
- 不得使用未解析变量、通配符或宽泛目录执行删除；
- 测试数据可恢复不等于自动获得操作授权。

### 5.4 最小证据

- 分支、提交、环境和配置摘要；
- 执行步骤与运行标识；
- 成功、失败、取消和并发观察；
- 日志、输出或数据现象；
- 发现问题、未运行项和风险结论。

### 5.5 失败闭环

Level 2 发现问题后：

```text
记录缺陷与复现证据
→ 在任务/修复分支开发
→ Level 0 独立 Review
→ 按影响执行 Level 1 回归
→ 合回长期集成分支
→ 重跑受影响的 Level 2 场景
```

通过后状态为 `SystemVerified`。是否触发分支动作由项目策略决定；默认是在长期集成分支稳定候选。

## 6. Level 3：真实外部环境版本验收

### 6.1 目标

验证本地自动化不能充分替代的真实外部系统、网络、权限、规模、长期运行和用户可见结果。

### 6.2 执行

- 默认需要项目负责人授权；
- 可以人工或半自动执行；
- Agent 可以检查配置、制定计划、分析日志和形成报告；
- 未授权不得连接或修改真实外部系统。

### 6.3 通过条件

- 需求指定的关键 Level 3 场景有结论；
- 关键业务结果、性能、失败与恢复符合批准标准；
- 剩余 `NotRun` 已批准例外并记录风险；
- 状态为 `ExternalVerified`。

通过后执行项目批准的稳定候选策略；默认允许申请稳定分支合并。无真实外部依赖的任务可以将 Level 3 标记为 `N/A`，但须说明理由。项目可预先批准常见 `N/A` 类别，只有超出预授权边界时再逐项审批。

## 7. 最终合并审核

最终合并审核者必须核对：

- 来源、目标分支和不可歧义冻结候选；
- Level 0–3 状态及适用性；
- Review 与测试是否绑定当前提交；
- 是否仍有阻塞目标分支的 `NotRun`；
- 文档、配置、迁移和工作区是否一致；
- 冻结后是否发生未复核代码变化；
- 最终执行仍需要的项目负责人授权是否已列为独立门禁。

结论只能是 `MergeApproved` 或 `MergeBlocked`。最终合并审核者只审核资格，不执行合并。

只有独立主分支合并任务可以在以下条件全部满足时执行：

- `MergeApproved` 仍绑定当前精确候选；
- 项目负责人对来源、目标和候选作出明确授权；
- 工作区和分支状态与审核时一致；
- 合并不需要改变已审核实现。

需要通过冲突处理改变实现时，`MergeApproved` 失效，必须建立修复候选并重新验证。合并完成状态为 `Merged`，不自动变成 `ReleaseReady`。

## 8. 测试重复与证据复用

开发者和 Reviewer 都执行测试是必要的独立验证，但应避免机械重复：

- 开发者运行修改点定向测试和受影响测试；
- Reviewer 复跑最小相关集合、抽查关键结果并增加反例；
- Level 1 在冻结候选上统一运行全量自动化；
- Level 2/3 只重复建立基线所需的快速测试，重点验证新增环境风险；
- 相同审核目标、命令和环境的稳定结果可以引用，但必须保留原始证据；
- 审核目标变化后按影响使证据失效；
- 测试输出应默认精简，只保留摘要与失败详情，减少时间和上下文消耗。

Reviewer 的主要价值是独立推理和反例，不是复制开发者全部工作。

按变更类型选择最低测试范围：

| 变化 | 默认动作 |
|---|---|
| 同一 `HeadSHA`，仅活动台账或证据排版变化 | 不重复代码 Review 或测试，只核对证据有效性 |
| 同一 `HeadSHA`，需求/设计审核基线实质变化 | 判断原 Review 是否失效，按影响重审 |
| 任务分支代码产生新 `HeadSHA` | 对新 `BaseSHA..HeadSHA` 执行受影响 Level 0 Review 与测试 |
| 已审核任务首次合入迭代分支 | 执行受影响持续集成检查 |
| 迭代候选冻结或组合发生变化 | 执行 Level 1 全量自动化与系统 Review |
| 仅人工/外部环境证据更新 | 只重跑受影响 Level 2/3 场景，不机械重复 Level 0/1 |

已知基线失败必须登记测试、首次证据、影响判断和责任人。候选未触碰相关路径时可以引用基线，不得每轮重新调查；本次变化可能影响该失败时必须重新验证。

## 9. NotRun 与例外

每个 `NotRun` 必须记录：

- 验收项和 Level；
- 原因；
- 可能遗漏的风险；
- 阻塞任务、长期集成分支、稳定分支或发布中的哪一步；
- 责任人和计划时间；
- 替代证据；
- 例外批准人和时间。

没有环境不能自动降低验收等级。可以由项目负责人接受风险，但不得改写为 `Passed`。

## 10. 风险适配

- 低风险纯逻辑任务可以简化 Level 1，Level 2/3 可为 `N/A`；
- 涉及生产入口、并发、持久化、安全或跨系统时，必须评估 Level 2；
- 涉及真实第三方行为、权限、网络或规模时，必须评估 Level 3；
- 项目可以预先批准低风险路线、常见 `N/A` 和角色兼任；只有超出预授权边界的简化才逐项升级审批。

## 10.1 不可歧义审核目标

Review 和验证可以绑定：

- Git commit；
- PR revision；
- diff/patch hash；
- 明确记录的稳定 worktree 快照。

真实编码任务默认必须绑定任务分支、`BaseSHA`、`HeadSHA`、`ReviewedCommitRange`、`ReviewedCommitSet` 和 `IntegrationMethod`。PR revision、diff/patch hash 或稳定 worktree 快照只适用于纯文档、调查或项目负责人事先批准的例外。worktree 路径不能替代 commit 身份。

目标发生实质变化后，Reviewer 必须重新评估哪些结论和测试证据失效。新 `HeadSHA` 自动使旧 Coding Review 失效；仅运行时台账、巡检时间或证据文档变化且代码 SHA 不变时，不自动触发代码重审。

```markdown

> Level:
> Branch:
> Commit:
> Environment:
> Executor:
> Reviewer:
> StartedAt:
> CompletedAt:
> Verdict:

## 1. 目标与关联验收项
## 2. 真实路径与替身
## 3. 命令或人工步骤
## 4. 结果与原始证据
## 5. Findings
## 6. NotRun、风险与例外
## 7. 分支动作建议
```

## 12. 审核清单

- [ ] 项目分支策略已配置，并保留等价状态和证据门禁；
- [ ] 开发、Review、迭代集成、系统 Review、最终审核和主分支合并权限已分离；
- [ ] 真实编码任务使用独立任务分支和精确 `BaseSHA..HeadSHA`；
- [ ] Level 0–3 的适用性、执行者和阻塞阶段明确；
- [ ] Level 1 通过后才执行项目配置的集成候选动作；
- [ ] Level 2 允许在项目指定集成候选上人工发现问题并返工；
- [ ] Level 3 和最终合并审核满足项目稳定候选门禁；
- [ ] 破坏性资源操作默认禁止，例外授权精确；
- [ ] 测试重复按风险控制，Reviewer 形成独立风险假设并按需验证反例；
- [ ] 所有结论绑定不可歧义审核目标；
- [ ] `TaskAccepted`、`Integrated`、`IntegrationVerified` 和 `ComponentVerified` 未被混用；
- [ ] 测试范围按实际变化选择，已知基线失败和证据复用有记录；
- [ ] NotRun 没有被伪装成通过。

## 13. 完成定义

只有当项目完成分支策略配置、各验收项映射到 Level 0–3、执行与 Review 责任明确、破坏性资源政策获批准、NotRun 和证据规则可执行后，本规范才可用于该迭代的合并判断。
