# 调度控制平面、开发任务文档状态面与恢复规范

> 规范版本：V2.4
> 规范状态：待审核
> 适用范围：使用 Coordinator、独立 Codex 子任务、周期巡检或其他异步执行机制的开发迭代
> 修订日期：2026-08-17

## 1. 目的与单一职责

本文规定多任务开发的控制平面，包括：

- 任务创建、身份绑定、文档状态生产/消费和幂等派发；
- 线程状态、开发任务状态和证据状态的分离；
- 开发任务文档状态交换区、派生审计缓存和协调租约；
- 暂停、热恢复、冷恢复和灾难恢复；
- 周期巡检的只读健康检查边界；
- 调度协议的 Canary 验收。

角色选择和提示词组装以 [`07-子Agent任务委派与提示词规范`](./07-子Agent任务委派与提示词规范.md) 为准；开发、Review、验证和合并门禁以 [`08-开发验证、代码审查与合并门禁规范`](./08-开发验证、代码审查与合并门禁规范.md) 为准。本文定义控制协议；每个项目的 `SharedRuntimeStatePath` 是该迭代任务运行状态的唯一真源，`CanonicalTaskDocumentPath` 保存任务定义与最近一次持久快照。

本规范不授权业务代码修改、外部操作、Review 通过或分支合并。

## 2. 核心原则

1. **文档状态驱动**：没有开发任务文档中更高版本的待消费状态和不可歧义目标，不启动跨任务读取或推进任务状态。
2. **状态分离**：线程是否运行、代码任务达到什么阶段、证据是否已消费必须分别维护。
3. **持久可恢复**：调度器不得只依赖聊天上下文、UI 标签、跨任务 API 事件或模型记忆。
4. **文档先发布、至少一次消费**：子任务先发布状态记录；允许重复读取同一文档版本，不允许重复产生副作用。
5. **最大安全状态**：恢复时只恢复到证据支持的最高状态，无法证明的内容保持待核实。
6. **控制面故障不污染业务状态**：任务创建、定向读取、工具协议或状态版本故障不得伪装成代码 `Blocked` 或 Review Finding。
7. **明确执行机制不可替代**：项目要求独立 Codex 子任务时，创建失败不得改用子 Agent、当前线程自做或其他机制兜底。
8. **按状态定向取证**：周期巡检以文档版本变化识别完成和求助；只有出现待消费记录时才读取其精确线程。

## 3. 三类状态

### 3.1 ThreadStatus

描述执行载体，不代表开发任务结论：

| 状态 | 含义 |
|---|---|
| NotCreated | 尚未请求创建 |
| Provisioning | 创建请求已接受，正式执行标识尚未绑定 |
| Running | 执行中或仍可继续 |
| Idle | 当前无活动；可能已经存在未消费 final |
| NeedsAttention | 请求输入、授权或发生可恢复异常 |
| Completed | 执行已结束；状态交换区出现对应 `PendingConsumption` 后，必须定向读取 final 才能判断任务结论 |
| Unavailable | 当前无法读取或执行载体丢失 |
| Cancelled | 已明确取消执行载体 |

Codex 返回正式 `threadId` 时可以直接登记执行标识；只返回 `clientThreadId` 等创建请求标识时，表示 `Provisioning` 成功，不得判定为创建失败。项目适配器应把实际字段映射到通用的 `CreationRequestId` 和 `ExecutionThreadId`。

### 3.2 TaskState

描述开发流程状态：

```text
Planned → Ready → InProgress → Submitted → InReview
  → ChangesRequested → ReworkInProgress → Submitted
  → TaskAccepted → MergePending → Integrated → IntegrationVerified
```

`Blocked`、`Cancelled` 是有证据的旁路状态。候选版本继续使用 `ComponentVerified`、`SystemVerified`、`ExternalVerified`、`MergeApproved` 和 `Merged`。

### 3.3 EvidenceState

描述一个事件或结论是否已经可靠消费：

| 状态 | 含义 |
|---|---|
| Unread | 已知可能存在但尚未读取 |
| Received | 已取得内容，尚未完成校验 |
| PendingVerification | 来源存在但暂时不能交叉验证 |
| Validated | 身份、目标和内容已经校验 |
| Rejected | 证据不属于目标任务、格式不可恢复或内容无效 |
| Superseded | 被新 `HeadSHA`、新候选或批准的替代证据取代 |
| Consumed | 已完成幂等状态转换或后续动作 |

以下推断一律禁止：

- `Idle`、`Completed` 或 UI 停止 ⇒ 没有 Review 结论；
- Git HEAD 未变化 ⇒ 没有 Review、求助或环境事件；
- 创建请求标识尚未绑定正式线程 ⇒ 创建失败；
- 测试 `NotRun` ⇒ Review 必然阻塞；
- 代码已在迭代分支 ⇒ 合规达到 `Integrated`。

## 4. 不可变执行基线

每次派发必须绑定以下基线；不适用时明确 `N/A` 及理由：

```text
CodeBaseSHA
RequirementsBaselineRef
DesignBaselineRef
TaskDocumentBaselineRef
ContextBaselineRef
```

`CodeBaseSHA` 是 V2.4 对代码基线的规范字段名。V2.3 制品中的 `BaseSHA` 作为兼容旧名读取；重建台账时映射为 `CodeBaseSHA`，新提示词和新证据不得同时输出两个名称。

文档基线必须使用不可变 Git commit/tree、受控文档 revision、diff hash 或项目负责人批准的稳定快照。不得把另一个持续变化工作区的绝对路径当作唯一设计基线。

真实编码任务默认使用 Git 身份：

```text
TaskBranch
WorktreePath
CodeBaseSHA
HeadSHA
ReviewedCommitRange
ReviewedCommitSet
MergeTarget
```

需求、设计或任务基线实质变化时，必须判断既有 Context、Review、测试和派发是否失效。代码 SHA 未变化不自动保持 Review 有效；是否失效取决于审核基线是否改变了目标行为或证明责任。

## 5. 开发任务文档状态面与派生审计缓存

### 5.1 唯一状态面

项目必须在详细开发任务文档中声明：

```text
CanonicalTaskDocumentPath
SharedRuntimeStatePath
TaskStateExchangeMode: SharedLocalJson
TaskStateWriteLockPath
StateUpdateToolPath
```

`SharedRuntimeStatePath` 必须是不进入 Git、所有 Coordinator、巡检和独立 worktree 都能访问并写入的同一个绝对 JSON 路径。它是任务状态生产、发现和消费确认的唯一实时真源。`CanonicalTaskDocumentPath` 中由 `TASK-STATE-EXCHANGE:BEGIN/END` 包围的结构化块只是最近一次持久快照；各 worktree 内的同名文档副本不得写运行状态。

状态区字段、`RecordID`、`SignalRevision`、`SignalState` 和并发写规则以 `04` §8 为准。任何角色都必须通过 `StateUpdateToolPath` 取得短时文件锁、重新读取最新 `StateRevision`、只修改自己有权写的记录，并在临时文件 `fsync` 与原子替换成功后才宣称状态已发布。

### 5.2 派生审计缓存

项目可以保留以下目录用于长日志、派发历史、租约和恢复备份：

```text
<project>/.codex-runtime/<iteration-id>/
├── events.jsonl
├── dispatches.jsonl
├── lease.json
└── backups/
```

该目录必须避免进入代码候选、Review diff、冻结 tree 和发布制品。它是从共享 JSON 派生的审计缓存，不得覆盖共享状态中的更高 `StateRevision`，也不得作为巡检发现任务完成的入口。

### 5.3 迭代级最小字段

```text
SchemaVersion, ProtocolVersion, IterationID, CoordinatorThreadID,
CoordinatorMode, Paused, CodeBaseSHA, RequirementsBaselineRef,
DesignBaselineRef, TaskDocumentBaselineRef, CanonicalTaskDocumentPath,
SharedRuntimeStatePath, StateUpdateToolPath,
StateRevision, CoordinatorConsumedRevision, UpdatedAt
```

### 5.4 任务级最小字段

```text
RecordID, TaskID, TaskType, Stage, InvocationID, ParentIterationID, Role,
ExpectedExecutionKind, ExpectedModel, ActualModel,
TaskBranch, WorktreePath, CodeBaseSHA, HeadSHA,
CreationRequestID, ExecutionThreadID, HostID,
ThreadStatus, TaskState, EvidenceState,
SignalRevision, SignalState, ProducedAt, ConsumedAt, ConsumedBy,
LastEventFingerprint, BlockerType, RecoveryConfidence, NextAction
```

`ExpectedModel` 是项目要求；无法验证 `ActualModel` 时记录 `Unknown`，不得自行宣称模型匹配。

## 6. 派生事件日志与幂等性

### 6.1 标准事件

至少支持：

```text
DispatchRegistered
ThreadCreationRequested
ThreadProvisioning
ThreadBound
ExecutionStarted
SubmissionReceived
SubmissionValidated
ReviewDispatched
ReviewResultReceived
ReviewResultValidated
FindingRegistered
ReworkDispatched
ReworkSubmissionReceived
TaskAccepted
IntegrationDispatched
Integrated
IntegrationVerified
NeedsAttention
ControlPlaneError
Paused
Resumed
RecoveryStarted
RecoveredEvidence
RecoveryApproved
```

### 6.2 事件身份

每个事件必须包含：

```text
EventID, ProtocolVersion, IterationID, TaskID, InvocationID,
EventType, SourceType, SourceID, TargetIdentity,
OriginalObservedAt, RecordedAt, Fingerprint, EvidenceState
```

`Fingerprint` 至少覆盖事件类型、任务、Invocation、目标 SHA/候选和规范化结果。重复读取同一事件时只能更新读取元数据，不得重复创建 Review、返工或集成任务。

### 6.3 因果关系

任何产生副作用的新派发必须记录：

```text
CausedByEventID
DispatchKey = IterationID + TaskID + Stage + TargetIdentity
```

同一 `DispatchKey` 已存在有效实例时，禁止再次派发。

## 7. 任务创建与身份绑定协议

1. 读取 `SharedRuntimeStatePath` 的最新 `StateRevision` 并获得未过期协调租约；
2. 校验 `Paused=false` 且不是 `RecoveryOnly`；
3. 生成唯一 `InvocationID` 和 `DispatchKey`；
4. 检查同任务、同阶段是否已有有效实例；
5. 校验任务类型、依赖、基线、分支、worktree、文件冲突、权限、模型和停止条件；
6. 先通过统一工具在共享状态创建唯一阶段记录并登记 `DispatchRegistered`，再调用项目要求的创建机制；
7. 返回正式执行标识时把 `ExecutionThreadID` 写回同一状态记录并登记 `ThreadBound`；
8. 只返回创建请求标识时登记 `ThreadProvisioning`，后续解析正式执行标识；
9. 创建调用失败时登记 `ControlPlaneError`，不得登记业务 `Blocked`；
10. 项目要求独立 Codex 子任务时，不得用 `spawn_agent`、当前任务实现或其他执行机制替代；
11. 创建成功后立即做一次可读性和任务身份检查，然后只等待状态交换区的 `StateRevision` 变化。

如果任务标题可配置，应包含稳定 `TaskID`、角色和 Invocation 短标识。提示词及 final 必须返回完整 `InvocationID`。

## 8. 文档状态生产与消费协议

标准循环：

```text
读取 SharedRuntimeStatePath 并获取租约
→ 比较 StateRevision 与 CoordinatorConsumedRevision
  → 出现 PendingConsumption：锁定精确 RecordID/SignalRevision
  → 仅按该记录的 ExecutionThreadID 定向读取详细 final/求助
  → 校验后更新汇总状态、标记 Consumed 并派发后续
  → 无新版本：只做文档与必要 Git 健康检查
```

事件消费顺序：

1. 读取待消费状态记录；没有 `PendingConsumption` 时禁止遍历任务系统寻找结果；
2. 以 `RecordID + SignalRevision` 计算幂等身份；
3. 仅对该记录绑定的 `ExecutionThreadID` 读取原始 final/求助内容；
4. 已消费则幂等忽略；
5. 记录 `Received`，不得先推进业务状态；
6. 校验 `ProtocolVersion`、`InvocationID`、`TaskID`、角色、分支和候选身份；
7. 用 Git、不可变文档或对应权威来源交叉验证事实；
8. 标记 `Validated`、`PendingVerification` 或 `Rejected`；
9. 仅 `Validated` 证据可以触发正常状态转换；
10. 在同一任务文档中写入汇总状态、消费确认和后续阶段记录；
11. 最后递增文档级 `StateRevision`、释放租约，并把长证据追加到可选审计缓存。

跨任务读取失败时保留 `PendingConsumption`，记录控制面错误并通知；下一轮仍只处理该待消费记录，不得退化为扫描所有线程，也不得把读取失败改写成业务 `Blocked`。

若 final 缺少结构化协议头但内容可能有效，应先要求同一执行载体补发“仅协议头/缺失字段”，不得直接否定结果或机械创建新任务。执行载体不可用时保留原始内容并进入 `PendingVerification`。

## 9. 证据归属与冲突处理

不同来源只证明其职责范围：

| 事实 | 权威来源 |
|---|---|
| 任务范围、依赖和授权边界 | 已审核任务文档 |
| 提交、祖先和分支包含关系 | Git |
| 开发是否正式提交 | 状态交换区记录 + Implementer final + Git 校验 |
| Review 结论 | 状态交换区记录 + 独立 Reviewer final |
| Review 审核的是哪个代码 | Reviewer final + Git SHA |
| 执行载体是否运行或结束 | 任务系统历史 |
| 项目负责人授权 | 明确用户消息或正式授权记录 |

用户提供的完整子任务结果应登记为 `ImportedEvidenceReceived` 并立即核验。无法访问原执行载体时标记 `PendingVerification`，不得被 UI 标签或旧缓存覆盖；同时不得在未经核验时直接授予 `TaskAccepted` 或执行合并。

来源冲突时必须并列记录。例如代码已经出现在迭代分支，但缺少 Review/集成证据时：

```text
CodePresence: PresentInIteration
ProcessState: IntegrationUnverified
RequiredAction: 审计来源、候选等价性和门禁，不自动回滚或宣布 Integrated
```

## 10. Review 执行状态与结论分离

Reviewer 输出必须分别包含：

```text
ExecutionStatus: Completed / Blocked
Verdict: Approved / ChangesRequested / NotIssued
BlockerType: None / RepositoryEnvironment / ToolRuntime / Authorization
```

规则：

- 测试 `NotRun` 不自动要求 `ExecutionStatus: Blocked`；Reviewer 仍可根据可验证反例形成 `ChangesRequested`；
- 工具调用格式、任务读取或模型执行协议异常属于 `ToolRuntime`，不是代码 Finding；
- 审核目标无法解析、仓库对象缺失等才属于 `RepositoryEnvironment`；
- 未经授权的真实外部操作属于 `Authorization`；
- `ExecutionStatus: Blocked` 时 `Verdict` 必须为 `NotIssued`；
- `Approved`/`ChangesRequested` 必须绑定精确审核目标；新 `HeadSHA` 自动使旧结论 `Superseded`。

执行协议错误第一次优先恢复同一任务并补齐输出；连续出现时按控制面故障升级，不计入代码 Finding 的返工轮次。

## 11. 周期巡检与通知

周期巡检必须读取同一个 `SharedRuntimeStatePath`。巡检提示词必须是可重复执行的持久协议，至少定义：状态路径、版本变化、消费条件、通知条件、停止条件和暂停行为。

每轮顺序：

1. 通过统一工具读取共享 JSON 和 `Paused`；
2. `Paused=true` 时只报告暂停，不读取或派发业务后续；
3. 获取租约，避免用户交互与心跳同时派发；
4. 比较 `StateRevision` 与 `CoordinatorConsumedRevision`，读取全部 `PendingConsumption` 记录；
5. 只对待消费记录定向读取其 `ExecutionThreadID`，校验并消费；
6. 无待消费记录时不调用任务列表或线程读取 API，只检查共享状态完整性、文档快照、必要 Git 依赖和租约健康；
7. 记录实际读取的文档版本、状态记录、定向线程和错误；
8. 释放租约并继续等待。

没有以下最小证据时不得报告“无变化”：

```text
TaskDocumentPath
StateRevisionBefore
StateRevisionAfter
PendingRecords
TargetedThreadsRead
GitHeadsChecked
ControlPlaneErrors
```

巡检不得只比较 Git HEAD，也不得重复发送已存在 `DispatchKey` 的指令；没有 `PendingConsumption` 时不得为了“确认无变化”逐线程读取。

## 12. 暂停、租约与并发协调

### 12.1 暂停

项目负责人要求暂停时：

- 先设置 `Paused=true` 并记录 `Paused` 事件；
- 停止新派发、返工、Review、集成和业务状态推进；
- 默认不取消已运行的子任务，除非项目负责人明确要求；
- 后续到达的事件可以原样保存为 `Received`，但恢复前不执行副作用；
- 周期巡检仅报告暂停状态或按项目配置静默。

恢复必须记录 `Resumed`，并先执行未消费事件对账。

### 12.2 协调租约

用户消息、手动继续和周期巡检可能同时触发 Coordinator。任何派发或状态转换前必须获得带到期时间的租约：

```text
LeaseOwner, LeaseID, AcquiredAt, ExpiresAt, Purpose
```

未获得租约的运行只能读取并报告，不得产生副作用。过期租约可以按恢复协议接管，但必须记录旧 Owner 和恢复原因。

## 13. 恢复协议

### 13.1 恢复级别

| 级别 | 条件 | 处理 |
|---|---|---|
| 热恢复 | 共享 JSON 完整，Coordinator 暂停、重启或切换 | 加载最新 `StateRevision`、接管租约、处理 `PendingConsumption` 后继续 |
| 冷恢复 | 共享 JSON 缺失、损坏或版本回退，但文档快照与 Git 存在 | 进入 `RecoveryOnly`，从最后有效文档快照和 Git 重建并审核后继续 |
| 灾难恢复 | 状态区与部分任务历史均不可访问 | 从已审核任务定义和 Git 恢复代码事实；缺失 Review/授权重新取得，不重复开发可验证代码 |

### 13.2 自动进入 RecoveryOnly 的条件

- 共享 JSON 不存在、无法解析、Schema 不兼容或 `StateRevision` 回退；
- Coordinator 身份改变且无法证明有效恢复点；
- 连续两个周期无法解释任务、线程和 Git 状态差异；
- 发现重复有效实例、未知合入、无法关联的 Review 或不一致候选；
- 状态记录缺口、重复 `RecordID + SignalRevision` 或消费版本倒退可能造成重复副作用。

`RecoveryOnly` 下禁止创建开发、Review、返工、集成或合并任务，禁止业务代码修改和状态推进。

### 13.3 冷恢复步骤

1. 优先读取 `SharedRuntimeStatePath`；其缺失或损坏时，从 `CanonicalTaskDocumentPath` 最后一个结构有效的快照恢复计划图、角色、依赖、基线、稳定状态和未消费记录；
2. 扫描 Git 分支、worktree、提交、祖先关系和迭代分支包含关系；
3. 仅对文档记录为 `PendingConsumption`、`PendingVerification` 或证据缺失的阶段，按其 `ExecutionThreadID` 定向发现执行载体；
4. 只读取上述目标任务历史；禁止把冷恢复重新实现为全量跨任务扫描；
5. 为 final、求助、提交、Review、返工和集成计算事件指纹；
6. 按来源职责交叉验证，并生成 `RecoveredEvidence`；
7. 对每项任务计算证据支持的最大安全状态；
8. 对冲突、缺失、错误执行机制和未知合入形成清单；
9. 通过统一工具写回新的共享状态并保存旧状态备份；在稳定门禁点把最新状态复制为开发任务文档持久快照；派生台账只记录长证据和租约；
10. 输出恢复报告；经项目负责人或项目批准的独立审计形成 `RecoveryApproved` 后才能退出 `RecoveryOnly`。

### 13.4 最大安全状态

- 仅发现任务分支 commit：`CodePresence=PresentInTaskBranch`、`TaskState=EvidenceIncomplete`；
- Implementer final 与 Git 均有效：最多恢复为 `Submitted`；
- 有效 `ChangesRequested`：恢复为 `ChangesRequested`，并检查是否已有新 Head；
- 有效 `Approved` 且目标等于当前 Head：可以恢复 `TaskState=TaskAccepted`，但 `RecoveryOnly` 仍禁止据此派发，必须先完成恢复审计；
- 当前 Head 已变化：旧 Review 标记 `Superseded`；
- 代码已在迭代分支但缺少合规集成证据：`IntegrationUnverified`，不自动回滚，也不宣称 `Integrated`；
- Review 历史丢失：重新 Review，不重新开发可验证提交；
- 授权记录丢失：重新取得授权，不从代码结果反推授权存在。

恢复事件必须带 `Recovered=true`、来源、原始时间、恢复时间和置信度：`Verified / Strong / Partial / Unknown`。只有 `Verified` 或项目规范明确允许的 `Strong` 可以支持正常状态转换。

## 14. 协议 Canary 与验收

真实高风险迭代启动前必须在无业务副作用场景测试控制平面，至少覆盖：

1. 创建只返回临时请求标识，能正确进入 `Provisioning` 并绑定正式执行标识；
2. 子任务早于巡检周期完成，先原子写入共享 JSON，Coordinator 在下一次状态检查时消费；
3. UI 或跨任务事件不可用，但共享 JSON 存在 `PendingConsumption` 时仍能精确定位结果；
4. final 缺字段时要求原任务补发，不重复创建执行实例；
5. 重复读取同一 `RecordID + SignalRevision` 不重复派发；
6. 用户粘贴完整结果时进入核验，而不是直接否定或直接批准；
7. 工具运行错误进入 `ControlPlaneError`，不污染业务 `Blocked`；
8. 新 `HeadSHA` 使旧 Review 失效；
9. `Paused=true` 后不产生任何新副作用；
10. 新 Coordinator 可以仅从共享 JSON 和必要 Git 事实热恢复；共享 JSON 丢失时可从开发任务文档快照冷恢复；
11. 删除派生台账后，共享状态不丢失且调度可以继续；
12. 要求 Codex 子任务时，失败不会触发其他执行机制兜底；
13. 不同 worktree 解析出的需求、设计和任务基线内容一致；
14. 两个同时触发的巡检最多一个获得写租约；
15. 不同 worktree 的子任务都通过统一工具写入同一个绝对 `SharedRuntimeStatePath`，不会写入各自文档副本；
16. 共享状态锁、版本复查和原子替换可以阻止两个生产者互相覆盖状态。

Canary 未通过时，真实业务任务保持 `Planned/Ready`，不得用真实开发验证调度协议。

## 15. 审核清单

- [ ] 线程、任务和证据状态已经分离；
- [ ] 唯一 `CanonicalTaskDocumentPath`、`SharedRuntimeStatePath`、Schema、短时锁、统一工具和原子写入明确；
- [ ] 派生审计缓存位置明确且不进入候选哈希，也不覆盖文档状态；
- [ ] 任务具有 Invocation、创建请求和正式执行标识；
- [ ] 所有派发具有幂等 `DispatchKey` 和因果事件；
- [ ] 代码与文档基线均不可歧义；
- [ ] 状态消费使用 `RecordID + SignalRevision`，没有待消费记录时不扫描线程；
- [ ] `clientThreadId` 等 Provisioning 成功未被当作失败；
- [ ] 项目要求的执行机制不可被未经授权替代；
- [ ] Review 执行状态和 Verdict 已分离；
- [ ] 周期巡检能证明实际读取状态交换区，并仅对 `PendingConsumption` 记录定向读取线程；
- [ ] 暂停和协调租约能阻止重复副作用；
- [ ] 热恢复、冷恢复和灾难恢复均有明确门禁；
- [ ] Canary 覆盖重复状态、早完成、删除派生台账、跨 worktree 统一写入和并发巡检；
- [ ] 恢复结果必须审核后才能重新派发。

## 16. 完成定义

只有当项目已配置唯一开发任务文档状态面、不可变执行基线、合法状态转换、幂等派发、暂停/租约、恢复协议和 Canary，并通过项目负责人审核后，Coordinator 才可调度真实高风险迭代。
