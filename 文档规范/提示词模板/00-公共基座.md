## 2. 执行载体与角色

```text
ExpectedExecutionKind: <由载体策略制品当前版本决定>
ExpectedModel: <expected-model-or-project-default>
ModelProvider: <载体策略制品允许的 provider 标识> / N/A
Role: Implementer / Reviewer / Integrator / Validator / Doc/Design Reviewer / Coordinator
PolicyVersion: <policy-version>                    # 派发时注入
PolicyArtifactDigest: <policy-artifact-digest>     # 派发时注入
CoordinatorEpoch: <current-epoch>                  # 派发时注入；不匹配即拒绝本任务
```

- `ExpectedExecutionKind` **不是静态枚举**：可用载体与分配规则由「载体策略制品」当前版本唯一定义（09 §12.4）；`ApprovedEquivalent` 仅在项目负责人批准等价机制时使用。
- 角色与载体不建立固定映射，由当前策略制品与任务需求共同决定（详见 `07` §2.1）。
- 每次派发必须注入 PolicyVersion/PolicyArtifactDigest/CoordinatorEpoch 三字段；Agent 发现字段缺失或不一致时停止并报告。
- Hermes 是 `Coordinator`，不代执行子 Agent 的 Git 与开发职责；子 Agent 不得冒充或吞并 Coordinator 职责。

## 3. 派发参数与沙箱分级（Hermes 注入）

```text
cwd: <工作目录绝对路径>
model: <实际使用的模型>
sandbox: read-only / workspace-write / danger-full-access
```

沙箱分级（依据《Hermes能力边界清单》§6）：

| 任务类型 | sandbox | 说明 |
|---|---|---|
| 所有 Codex 派发（含 Review/Validator） | danger-full-access | V3.0 统一权限；Reviewer/Validator 受代码不可变约束（09 §7.3）|
| 写文档 / 写证据文件 | workspace-write | 不触碰 `.git` 的文档工作 |
| **需要 git 提交**（开发 / 集成（含合并）/ 文档设计） | danger-full-access | `.git` 在 workspace-write 下为 protected path，会拦 git |

所有 Codex 派发统一 `danger-full-access`（V2.5 只读沙箱无法编译运行测试）。Reviewer/Validator 受**代码不可变约束**：在隔离 detached 验证工作区审查，前后 HEAD/tree 对账，不得改业务源码/commit 候选/merge。Hermes 不代执行 git，worktree 创建由 Implementer 自办。

服务或计划任务管理操作、跨 profile 服务操作等特权操作须先获 Richy 授权并写 OPS-AUDIT 记录（具体工具清单见实例登记）；安全拦截=转人工，禁止绕过（适用本部署的特权操作治理规则，具体规则载体登记于实例记录）。

## 4. 台账与状态发布

```text
LedgerLocation: <Hermes 台账位置，项目目录内、不进 Git>
CanonicalTaskDocumentPath: <Git 管理的任务定义/快照路径>
StateRecordID: <本阶段唯一记录>
```

- Hermes 台账（本地 JSON 状态文件 + 可选 SQLite）是任务运行状态的**唯一真源**；`TASK-STATE-EXCHANGE` 块是开发任务文档中的 **Git 持久快照**，二者分工由 `09-Hermes调度与运行时台账规范` 规定。**台账绝不提交至 Git——即便有 ```danger-full-access``` 提交权限，任何 add/commit 也不得包含台账文件**（防循环引用/自包含哈希）。
- 执行 Agent **不直接写台账**。完成、求助、阻塞或形成 Review/集成结论时，通过其载体通道输出**结构化协议头**（见各角色模板），由 Hermes 通过事件源 + 定时对账兜底消费后**幂等写入台账**。
- 台账写入幂等由 `DispatchKey = IterationID + TaskID + Stage + TargetIdentity` 与 `RecordID + SignalRevision` 去重保证；调度权唯一性由 `CoordinatorEpoch` FencingToken 保证（非当前 Epoch 的副作用写入一律拒绝），不再以"单实例无锁"为前提。

## 6. 不可变文档基线

```text
RequirementsBaselineRef: <ref-or-N/A>
DesignBaselineRef: <ref-or-N/A>
TaskDocumentBaselineRef: <ref>

```

不得以另一个持续变化工作区路径替代这些内容身份。

## 7. 共同约束

1. 保护用户和其他任务已有改动，不得覆盖无关变化。
2. 未经授权不得连接、修改或删除真实外部资源；破坏性操作停止并请求精确授权。
3. 所有测试和结论绑定审核目标、环境、命令或步骤与时间；未运行项标记 `NotRun`。
4. 只使用角色模板允许的状态；发生冲突时使用该角色的阻塞或失败状态，并附证据。
5. 最终输出列出证据、限制和剩余风险，不能只说"已完成"。
6. 严格遵守角色的 Git 权限；worktree 只是工作目录，不能替代分支和 commit 身份。
7. 最终输出必须先给出角色模板规定的结构化协议头，并原样返回 `ProtocolVersion`、`IterationID`、`TaskID`、`InvocationID`、`StateRecordID`；不得省略或自行改写身份。
8. 若实际执行机制、模型、沙箱、分支、基线或文档 Ref 与上述值不一致，停止并报告；不得在错误目标上继续。
9. 本任务只能履行 `<role>` 的职责边界；不得自行批准自己的实现，不得把开发与 Review、合并执行与审查混为同一执行主体。
10. 测试职责分层（防 token 浪费）：Level 0 由 Implementer 跑一次并落证据；Reviewer 基于 diff + L0 证据审查、不重跑全套单测；Level 1 + 回归由 Validator 仅在 merge 前跑全量一次。
